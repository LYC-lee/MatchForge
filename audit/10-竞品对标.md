## 1. 领域概述

### 1.1 MatchForge 真实定位与能力基线（项目内证据）

**【已确认事实】** MatchForge 首期定位已从宽泛的"AI 供需对接平台"收窄为"**电子元器件 AI 替代料寻源助手**"（`docs/AI供需对接平台-产品需求文档.md:20`）。核心闭环为：自然语言采购需求 → AI 解析规格 → 替代料推荐 → 供应商匹配 → 询价单生成 → 分级线索推给上游（`README.md:5`）。技术实现为通义千问 DashScope + LangGraph（Supervisor + 6 子智能体：parse/normalize/alternatives/match/gen_rfq/grade，见 `README.md:27`、`ai/agents/` 目录），数据层为 MySQL 8.0 + Milvus 2.4 + Neo4j + Redis 7（`README.md:10-13`）。

**【已确认事实】** 目标用户画像：深圳 30-200 人中小硬件制造商/EMS 代工的采购专员/主管（`docs/AI供需对接平台-产品需求文档.md:79`），成功标准为"10 分钟内拿到 2-3 个有依据的替代建议 + 可直接发送的询价单"（同文件:85）。

**【已确认事实】** 数据资产现状（实测统计）：
- 供应商种子数据 **35 家**（`data/suppliers/suppliers.json`，字段含 qualifications/rating/status/main_category/products，且含静态 price/lead_time_weeks/in_stock 字段，见该文件:30-32 示例）；
- 替代料交叉引用 **实际 36 组**（`data/alternatives/alternatives.json` 的 groups 数组长度；但该文件 metadata 自称 `total_groups: 30`，自相矛盾），覆盖 5 个品类（MLCC 电容、贴片电阻、二极管、连接器、MCU），置信度 0.70-0.99，来源类型含"Datasheet 交叉引用、行业交叉表、LLM 推理"；
- 标准参数字典 **81 条**（`data/dictionary/dictionary.json` items 长度）。

**【已确认事实】** 生命周期/EOL 能力：数据模型有 `lifecycle_status` 字段（`api/models/__init__.py:120`，Enum: active/nrnd/eol/obsolete/unknown），替代料智能体有 EOL 红线过滤逻辑（`ai/agents/alternatives.py:254-257`），解析提示词要求输出生命周期状态（`ai/prompts/parse.py:19`）。但 EOL 数据从何处持续获取、种子数据中该字段的真实填充率，**【尚未验证】**。

**【已确认事实】** 项目自我划定的边界（`docs/AI供需对接平台-产品需求文档.md:60-64`）：不做完整供应商 CRM、行情预测、完整 BOM 批量优化；不承诺实时库存/报价/交期；并设表述红线——未经供应商实时确认只能表述"能力匹配"，不得表述"确认有货"（同文件:64）。远期愿景（双边平台、上游线索付费、撮合、供应链金融）明确"不是首期功能"（同文件:66-67）。

**【已确认事实】** 商业模式仍是待验证假设：PRD 将"供应商愿为真实线索付费"标注为 `[高风险假设]`，验证节点为"MVP 前"、失败预案为"转 SaaS 订阅"（`docs/AI供需对接平台-产品需求文档.md:615`）；"下游免费、上游线索付费""不碰交易、只做信息撮合与线索"仍是供应商访谈问题而非已决策略（同文件:646、653）。报价对比、BOM 批量、行情数据、线索分级收费均列为 Could/P2 可延后项（同文件:581）。

**【已确认事实】** 数据获取计划的合规隐患：PRD 规划"标准元器件"数据来源为"立创/Digikey/Datasheet 库，定期抓取"（同文件:534），同时自问"爬取立创/1688 → 法律风险"，对策仅为"优先官方 API + 法务确认，需法务介入"（同文件:634）。

### 1.4 与项目方行业判断（`docs/电脑制作全链路产业链分析.md`）的印证与反驳

**印证（联网证据支持项目方判断）：**
1. "授权分销 vs 现货贸易二元结构，价格透明度差异大"（该文件:532）——印证：云汉（数据合作+自营）、猎芯（现货在库）、华强北（华强电子网）的市场分层清晰存在。
2. "缺料管理是核心痛点，需多层替代料策略"（:533）——印证：云汉芯应急、猎芯 BOM 闪配宝、Sourcengine 季度交期报告、智芯谷 40 维预警均围绕缺料。
3. "国产替代寻源需求强烈，但国产器件参数/质量数据不透明，替代验证周期长"（:535）——印证：立创配套连接器、芯查查、第三方平台"国产品牌展示+兼容型号推荐"趋势（bomyg.com 选型文）。
4. "元器件数据分散，Octopart/Findchips 覆盖国际品牌较好，国产元器件数据不足"（:536）——印证：Octopart/Findchips 数据源以国际授权分销商为主；国内以立创/云汉各自为战，无统一数据层。
5. "SiliconExpert/Z2Data 提供生命周期、停产预警、替代料推荐"（:528）——方向印证：Supplyframe DSI、智芯谷预警证明该能力已成平台标配。

**反驳/纠正（项目方材料与事实冲突）：**
1. **【严重失真】** 该文件:492 称"云汉芯城 2024 年营收 112.3 亿人民币"，而招股书口径 2024 年主营业务收入为 **25.77 亿元**（[readtheone IPO 数据](https://www.readtheone.com/ipos/301563)），**高估约 4.4 倍**。基于错误体量做出的竞争强度判断会系统性偏差。
2. **【覆盖不全】** 该文件的"中国分销/电商"表（:487-492）仅列立创、云汉两家，未覆盖猎芯、硬之城、华强电子网，更未覆盖芯查查、智芯谷、Supplyframe XQ 等 **AI 原生数据/选型竞品**——竞争格局判断滞后于 2025-2026 年实际。
3. **【表述偏差】** 该文件:492 称云汉"服务超 3 万家电子制造企业（含华为、中兴、比亚迪等）"，来源为第三方市场监测站点；与云汉"中小批量小散临急"的官方定位及招股书客户结构存在张力，应降级为【尚未验证】。
4. **【内部不一致】** 该文件 9.2 节建议 MatchForge 切入链路为"产品/BOM → 缺料识别 → 替代料推荐 → 供应商匹配 → RFQ 询价 → **报价比价 → 采购决策**"（:856-864），但 PRD 将"报价对比"列为 Could/P2 可延后（`docs/AI供需对接平台-产品需求文档.md:581`），产品闭环实际停在 RFQ 生成——自家行业判断与产品范围相互矛盾。

### 1.5 综合对标结论

**MatchForge 已具备的优势（相对竞品）：**
1. 【已确认事实】**AI 原生交互架构**：LangGraph Supervisor + 6 智能体全链路（`ai/agents/`），自然语言直接进需求；竞品多为"搜索/规则引擎 + 后期叠加 AI 模块"（云汉 HiBOM 是 SaaS 工具而非对话式全链路）。对话式"说人话→出替代+询价单"的体验上限更高。
2. 【已确认事实】**合规与信任文化前置**：PRD 表述红线（只能"能力匹配"不得"确认有货"，PRD:64）、替代需人工确认（PRD:61）——在 B2B 信任敏感领域是正确的风控基因。
3. 【已确认事实】**冷启动策略方向正确**：单边工具 + 窄品类（PRD:636），符合云汉（先自营商城）、京东工业（先自营 MRO）先单边后双边的历史路径。
4. 【合理推断】**知识图谱+向量双引擎的替代推理**（Neo4j 替代关系 + Milvus 语义匹配 + RAG 知识库）在国内竞品公开信息中未见同构披露——但【尚未验证】竞品内部是否已有类似实现，不能宣称"独有"。

**明显落后项（有证据的差距）：**
1. 数据规模差 **4-5 个数量级**：35 供应商/36 替代组/81 字典 vs 立创 56 万 SKU、云汉 200 万型号、Supplyframe 6 亿元器件。
2. 无实时价格/库存/交期数据（PRD 自设边界），而这是 Octopart/Findchips/Sourcengine 的核心价值；suppliers.json 中的 price/in_stock 为静态种子字段（`data/suppliers/suppliers.json:30-32`）。
3. 无 BOM 批量解析能力（PRD 列为 Could/P2），而云汉 HiBOM（90%+/300ms）、硬之城（自称 3 秒报价）已量产。
4. 无预警/订阅机制，对标 Findchips Part Alerts、智芯谷 40 维预警。
5. 无开放 API 与生态集成，对标 Nexar GraphQL API（已进 MCP 生态）、立创开放平台。
6. 无可信度基础设施（质检/担保/正品/审核），对标猎芯质检中心、立创自营担保、1688 星级名片。
7. 无获客通道（EDA/社区/SEO/内容），对标嘉立创 EDA 免费入口、Supplyframe 免费 ECAD 模型（100 万注册）、Octopart 700 万次/月 SEO 流量。

**头部有而项目没有的能力清单：** 实时可得性数据（Supplyframe/Findchips）、BOM 批量解析与报价（云汉/硬之城）、缺货/停产/价格预警（Findchips/智芯谷）、质检信任体系（猎芯）、EDA/PLM 集成（嘉立创 EDA、Supplyframe×Teamcenter、Nexar×Altium 365）、开放 API 生态（Nexar/立创）、供应链金融（云汉/京东工业）、企业级采购 SaaS（DirectSource/太璞）、内容情报（Sourcengine 交期报告/Supplyframe 博客）。

**没必要模仿的能力（MVP 阶段明确排除）：** 自营仓储现货（立创 10 万㎡仓库）、PCB/SMT 制造（嘉立创/云汉芯智造/硬之城智造中心）、自建质检实验室（猎芯 X-RAY）、供应链金融（资金与牌照门槛）、全品类 MRO 扩张（震坤行 32 条线）、企业级 PLM/ERP 深度集成（Supplyframe×Teamcenter——客户画像不符）。这些均为重资产/重资质能力，与"工具先行、不碰交易"定位冲突。

**当前最值得借鉴的三项能力（按投入产出排序）：**
1. **云汉 HiBOM 的 BOM 批量场景**：把单条 NL 查询扩展为"上传 BOM → 批量解析 → 缺货行自动出替代"。直接命中画像用户"接研发 BOM 询价"的日常工作（PRD:81），且 PRD 已有 BOM 批量 Could 项可提前；不需要交易闭环即可交付价值。
2. **Findchips Part Alerts 式订阅预警**：缺货/停产/价格变动主动提醒。低成本高留存，用现有 MySQL+智能体+定时任务即可实现 MVP 版，是把"一次性工具"变成"持续服务"的留存抓手。
3. **Nexar/立创开放平台的官方 API 数据合作**：以官方 API（立创开放平台、云汉数据合作业态、未来 Nexar 中国区）替代爬取（PRD:534/634 自标法律风险），合规获得价格/库存/生命周期数据，同时消灭数据冷启动的最大合规隐患。

**差距分类汇总：**
- **功能差距**：BOM 批量解析、报价回收与比价、预警订阅、开放 API、供应商档案评分体系（可借鉴 1688 星级名片）——均可通过开发追赶。
- **数据差距**：SKU/型号库规模、实时价格库存交期、EOL/PCN 情报流、替代库规模、真实成交数据——需数据源合作+时间积累，纯开发追不上。
- **工程差距**：大规模数据管道与更新机制、90%+ 准确率的工业级 BOM 解析、分销商 API 对接网络、高并发搜索——中等周期可追。
- **商业模式差距**：竞品已验证（自营差价/交易佣金/SaaS 订阅/原厂广告/供应链金融），MatchForge 唯一的线索付费假设未验证——需客户访谈与试点验证，非开发问题。

**短期无法通过开发解决的差距（需 BD/时间/资本）：**
1. 供应商与原厂关系网络（云汉 500+ 原厂、京东工业 15.8 万家、华强北商户网络）——BD 积累；
2. 正品与质检信任（自营仓、X-RAY 实验室）——重资产或第三方合作；
3. 流量入口与品牌（250 万注册用户、700 万次/月搜索、1200 万月触达）——内容/社区/工具长期运营；
4. 真实交易数据飞轮（成交价/交期/履约表现）——必须先有交易量；
5. 资金与牌照（供应链金融账期）——资本与风控能力。

## 2. 问题清单

### 问题 1：数据资产与竞品差 4-5 个数量级，冷启动数据路径依赖有法律风险的爬取
- **所属模块**：数据层（data/）+ 战略规划
- **严重程度**：致命
- **影响范围**：全部核心场景（替代推荐、供应商匹配、搜索）
- **发现依据**：`data/suppliers/suppliers.json`（实测 35 家）、`data/alternatives/alternatives.json`（实测 36 组/5 品类）、`data/dictionary/dictionary.json`（实测 81 条）；`docs/AI供需对接平台-产品需求文档.md:534`（"立创/Digikey/Datasheet 库，定期抓取"）、:634（"爬取立创/1688 → 法律风险"）；对立证据：立创 56 万 SKU（`docs/电脑制作全链路产业链分析.md:491`）、云汉 200 万+型号（cnblogs 排名文）、Supplyframe 6 亿+元器件（Siemens 新闻）
- **问题描述**：MatchForge 的全部推荐能力建立在 35 家供应商、36 组替代、81 条字典的静态种子数据上；PRD 规划的补数路径是"定期抓取"立创/Digikey/1688，且自身已识别法律风险但无落地方案（仅"需法务介入"）。竞品中任何一家的数据规模都超出本项目 4 个数量级以上。
- **可能后果**：上线即"数据空心"——用户查询命中率低、替代推荐覆盖率不足、Demo 之外无实用价值；若强行爬取则面临法律与封禁风险；数据空心会同时摧毁"AI 准确"的唯一卖点。
- **推荐解决方案**：(1) 立即停止以爬取为主的数据规划，转为官方 API 合作：立创开放平台、云汉数据合作业态、Nexar API（国际料号）三路并行；(2) 窄品类深做：仅 MLCC/贴片电阻两个品类做到参数级完备（对标智芯谷 1000+ 末级分类的纵深思路），而非 5 品类浅铺；(3) 把"人工 curate 的 36 组替代"作为可信卖点而非短板——标注来源与置信度（数据已有 confidence 字段），做"精而可信"的差异化。
- **修改成本**：高
- **优先级**：P0
- **是否影响当前上线**：是（数据空心直接导致工具不可用）
- **是否需要重构**：否（数据结构可保留，需重建数据获取管道与填充流程）
- **验收标准**：上线前 MLCC+贴片电阻两个品类的标准元器件库 ≥5000 条且 100% 标注数据来源（官方 API/授权数据）；供应商库 ≥200 家且均有真实合作确认记录；无任何未授权的爬取数据入库；随机抽 50 个画像用户真实需求，系统能给出有来源的替代/供应商答案的比例 ≥70%（对齐 PRD:616 的"替代命中率≥70%"门槛）。

### 问题 2：核心差异化"AI 替代料推荐"已不稀缺，且竞品用交易闭环承接而本项目在 RFQ 处断裂
- **所属模块**：产品定位 / 全链路（ai/ + api/）
- **严重程度**：致命
- **影响范围**：竞争定位、商业模式成立性
- **发现依据**：云汉 HiBOM 已量产"BOM 解析 90%+ 准确率、单行 <300ms、缺货物料替代推荐"（CFi 新股介绍 2025-11-04）；硬之城自称 BOM 报价 72h→3s、配齐率 98%（公众号十周年文）；猎芯 BOM 闪配宝+现货在库（腾讯新闻 2025-10-31）；智芯谷替代推荐对比服务（电子发烧友 2026-03-31）；Supplyframe XQ 智能选型（知乎专栏）；本项目闭环止于 RFQ 生成（`README.md:5`、`ai/agents/gen_rfq.py` 之后无报价回收模块），PRD 将"报价对比"列为 Could/P2（`docs/AI供需对接平台-产品需求文档.md:581`），与自家产业链分析 9.2 建议链路（含"报价比价→采购决策"，`docs/电脑制作全链路产业链分析.md:856-864`）矛盾
- **问题描述**：2025-2026 年"AI 解析+替代推荐"已从稀缺能力变为平台标配；且竞品的推荐直接挂在可成交的库存上（云汉/立创自营现货、猎芯现货在库），用户从推荐到下单一步完成。MatchForge 的推荐只能停在"能力匹配"（PRD:64 红线），RFQ 发出后无报价回收、无比价、无订单承接——用户得到建议后仍要回到竞品平台完成交易。
- **可能后果**：MatchForge 沦为竞品的"前端流量插件"——用户在 MatchForge 拿建议、去立创/云汉下单；上游供应商因无法看到成交转化而拒绝为线索付费（PRD:615 高风险假设直接落空）。
- **推荐解决方案**：(1) 把定位从"替代推荐"升级为"**替代决策支持**"：输出参数差异表+风险标注+验证清单+来源证据（代码已有参数差异与红线机制雏形），做到竞品不做的"工程师级可信论证"；(2) 补齐 RFQ 后半程：报价回收（供应商链接/邮件回传结构化报价）+比价表，实现自家 9.2 链路；(3) 与 1-2 家现货平台谈 API 级"推荐→可买"跳转分成，先借竞品的交易闭环变现，而非自建交易。
- **修改成本**：中
- **优先级**：P0
- **是否影响当前上线**：是（闭环断裂则双边故事不成立）
- **是否需要重构**：部分（需在 gen_rfq 之后新增报价回收/比价模块与数据表）
- **验收标准**：用户发出 RFQ 后，系统能在同一界面回收 ≥2 家供应商的结构化报价并生成比价表；每条替代推荐附带参数差异、风险红线检查结果与数据来源；试点期内至少 1 条真实线索完成"推荐→报价→成交意向"全流程并有记录。

### 问题 3：商业模式唯一假设"上游线索付费"未验证，且无已落地的备选变现路径
- **所属模块**：战略/商业模式
- **严重程度**：严重
- **影响范围**：项目存续、融资叙事
- **发现依据**：`docs/AI供需对接平台-产品需求文档.md:615`（"供应商愿为真实线索付费 [高风险假设]，验证节点 MVP 前，预案转 SaaS 订阅"）、:646（仍为访谈问题）、:653（"不碰交易只做信息撮合"未定）；竞品变现均已验证：云汉（自营差价+供应链金融）、立创（自营差价+制造）、京东工业（商品+服务，2024 营收 204 亿）、Octopart（原厂/分销商付费曝光）、Supplyframe（企业 SaaS）
- **问题描述**：项目的全部收入想象押注在"供应商为分级线索付费"一个未验证假设上；预案"转 SaaS 订阅"只在风险表中出现一次，无产品设计、定价或客户验证支撑。而"线索付费"在元器件行业的成立前提是线索能带来成交——恰好被问题 2 的闭环断裂削弱。
- **可能后果**：MVP 试点后发现供应商不付费，此时再转 SaaS 订阅需重做产品包装与定价，错过窗口期；无法回答投资人"谁付钱、为什么、付多少"。
- **推荐解决方案**：(1) 在 MVP 试点前完成 ≥5 家供应商付费意愿深访（PRD 已列但未执行），拿到"愿意试付/按成交付费/拒绝"的明确分布；(2) 设计双轨变现：下游采购侧 SaaS 订阅（替代决策支持+BOM 管理+预警订阅，对应问题 2、问题 5 的能力）作为主路径，上游线索/曝光付费作为辅路径——Octopart 证明"供应商为曝光付费"成立，但前提是平台有采购方流量；(3) 试点期即埋点记录每条线索的后续转化，为定价积累证据。
- **修改成本**：低（主要是访谈与定价设计，非开发）
- **优先级**：P0
- **是否影响当前上线**：否（不影响功能上线，但影响上线后的存续）
- **是否需要重构**：否
- **验收标准**：形成书面访谈纪要 ≥5 家供应商、≥5 家采购方；明确主/辅变现路径与试点定价；系统中每条线索具备转化状态跟踪字段；试点复盘时能回答"单条线索价值多少钱"。

### 问题 4：可信度机制空白——无供应商审核、质检、担保、正品保障体系
- **所属模块**：供应商体系（api/models + data/suppliers）
- **严重程度**：严重
- **影响范围**：双边信任、供应商入驻、品牌
- **发现依据**：`data/suppliers/suppliers.json` 仅含 qualifications（自填资质数组）/rating（静态数值）/status 字段，无审核流程、质检记录、交易担保、投诉机制的任何证据（grep 全库无相关模块）；对立证据：猎芯自建质检中心含 X-RAY/电气性能/可焊性检测（ichunt.com 官网）、立创自营正品担保（搜狐 2022-08）、华强电子网优质供应商评选（hqew.com 专题）、1688 找工厂星级名片+实力商家认证（知乎/大数跨境）
- **问题描述**：B2B 元器件交易的第一性问题是"货真不真"。所有直接竞品都在信任基础设施上重投入，而 MatchForge 计划把供应商推给采购方（线索分级），却只有 35 家自填资质的种子数据和一个静态 rating 字段。假货风险直接由 MatchForge 品牌承担。
- **可能后果**：一次假货/翻车事件即可摧毁平台信誉；供应商分级（grade.py 线索分级）因无真实履约数据而只能基于自填信息，分级结果无说服力，上游不会为之付费。
- **推荐解决方案**：(1) MVP 阶段采用"白名单邀请制"供应商入驻：人工审核营业执照、授权代理证书、往期交易凭证，审核记录入库；(2) 借鉴 1688 星级名片，把供应商档案结构化完整度（产线/产能/认证/检测设备）做成质量分并展示；(3) 质检不自建，与第三方检测机构（如已服务竞品的检测机构）谈按次合作，作为增值服务转售；(4) 红线声明：平台展示的资质均经人工核验，核验日期入库可查。
- **修改成本**：中
- **优先级**：P1
- **是否影响当前上线**：部分（上线演示可用种子白名单，但对外招商必须先有审核流程）
- **是否需要重构**：否（新增审核状态机与档案评分字段即可）
- **验收标准**：供应商入驻有明确的审核流（提交→核验→准入/拒绝）与核验记录表；前台展示的每家供应商有"档案完整度评分"与"最近核验日期"；首批供应商 100% 白名单人工审核；出现假货投诉时有下架与追溯流程文档。

### 问题 5：无实时可得性数据（价格/库存/交期），"寻源"答案无法回答"哪里能买到"
- **所属模块**：数据层 + 供应商匹配智能体（ai/agents/match.py）
- **严重程度**：严重
- **影响范围**：用户核心价值兑现、与竞品体验差距
- **发现依据**：PRD 明确不做"未经供应商确认的实时库存、报价、交期承诺"（`docs/AI供需对接平台-产品需求文档.md:62`），红线为只能表述"能力匹配"（:64）；suppliers.json 中的 price/lead_time_weeks/in_stock 为静态种子字段（`data/suppliers/suppliers.json:30-32`）；对立证据：Findchips/Octopart 的核心就是实时价格库存聚合、云汉交付时效 2-5 天、Sourcengine 实时市场数据
- **问题描述**：采购的真实问题是"这个料现在哪里买得到、多少钱、多久到"。竞品的回答是可点击成交的实时报价；MatchForge 的回答是"这些供应商能力上可能匹配，请自行询价"。价值落差巨大，且 10 分钟成功标准（PRD:85）不包含拿到真实报价。
- **可能后果**：用户把 MatchForge 当"供应商黄页+替代百科"用一次即流失；无法形成使用频率与数据积累。
- **推荐解决方案**：(1) 接入立创开放平台等官方 API，对推荐结果做"参考可得性"标注（明确标注数据时间与来源，遵守 PRD 红线表述为"参考"而非"承诺"）；(2) 对 RFQ 已回收报价的供应商，展示"最近一次真实报价与响应时长"（来自自身闭环数据，合规且独特）；(3) 把报价响应速度/报价率做成供应商分级（grade.py）的核心因子，形成自家数据飞轮。
- **修改成本**：中
- **优先级**：P1
- **是否影响当前上线**：部分（MVP 可先无实时数据，但必须有明确的产品化表述与路线图）
- **是否需要重构**：否
- **验收标准**：≥60% 的推荐型号能展示至少一个来源的"参考库存/价格"并标注数据时间与来源；每家活跃供应商有"近 30 天报价响应率/平均响应时长"指标；所有可得性表述通过 PRD:64 红线检查（无"确认有货"表述）。

### 问题 6：无开放 API 与生态集成，缺乏数据飞轮入口
- **所属模块**：后端 API（api/）+ 战略
- **严重程度**：中等
- **影响范围**：生态合作、数据积累、企业客户接入
- **发现依据**：`api/` 仅有服务自身前端的 FastAPI 路由（`api/routers/`、`api/routes/`），无对外开发者 API、API Key 体系、embed 组件的任何证据；对立证据：Nexar GraphQL API 免费开放且 2025-12 已进入 MCP/AI Agent 生态（GitHub nexar-mcp）、立创开放平台、云汉数据合作业态、Supplyframe embeds
- **问题描述**：海外头部把 API 作为数据飞轮入口（分销商/原厂/软件商接入越多，数据越全，搜索越准）；MatchForge 无任何对外接口，未来的 ERP/EDA/企业微信集成、供应商系统对接都无落点。AI Agent 时代，不能被 Agent 调用的数据源会在 Agent 工作流中隐形。
- **可能后果**：被排除在企业采购系统与 AI 采购助手的工作流之外；数据只能进不能出（也不能被生态反哺），长期数据差距固化。
- **推荐解决方案**：MVP 阶段不做完整开放平台，但预留最小能力：(1) 把"替代查询/供应商匹配"封装为 2-3 个稳定的只读 API，配 API Key 鉴权（可复用 api/auth.py 体系）；(2) 在 roadmap 中明确 MCP Server 形态（对标 nexar-mcp），让采购方的 AI 助手能调用 MatchForge；(3) 对上游供应商提供"报价回传"结构化接口（邮件解析+链接填报亦可）。
- **修改成本**：低-中
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：提供 ≥2 个只读 API（替代查询、供应商匹配），有鉴权、限流与文档；至少 1 个外部调用方（试点客户的内部系统或演示 Agent）成功对接；报价回传通道被 ≥3 家供应商实际使用。

### 问题 7：无预警/订阅机制，工具无留存抓手
- **所属模块**：产品功能（缺失模块）
- **严重程度**：中等
- **影响范围**：留存率、使用频率、SaaS 订阅可行性
- **发现依据**：全项目无 alert/subscription/watch 类模块（api/、ai/ 检索无对应实现）；对立证据：Findchips Part Alerts（库存/价格变动邮件提醒，findchips.com 官网）、智芯谷近 40 维度实时预警（电子发烧友 2026-03）、Sourcengine 季度交期报告订阅
- **问题描述**：MatchForge 当前是"有事才来"的单次工具；竞品的预警订阅让用户"没事也被服务"——缺货、停产、涨价主动推送。对"跟缺货料"的采购画像（PRD:83）而言，预警恰是最高频的被动需求。
- **可能后果**：用户无回访理由，MVP 数据（活跃度、留存）难看；未来 SaaS 订阅缺乏持续价值支撑。
- **推荐解决方案**：(1) 实现最小版"关注列表"：用户对型号/替代组点关注，系统周期性（接 API 数据或供应商报价变动）比对并邮件/企业微信推送；(2) 预警维度从少做起：先是"我询过价的型号报价更新"，再是"关注型号的生命周期/缺货信号"；(3) 与问题 5 的 API 数据接入共用管道，避免重复建设。
- **修改成本**：低-中
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否（新增订阅表+定时任务+推送通道）
- **验收标准**：用户可关注任意型号并收到至少一类变动提醒；试点期预警邮件/消息的打开率 ≥30%；预警功能带来 ≥20% 的周回访提升（埋点可证）。

### 问题 8：生命周期（EOL/PCN）数据机制有设计但无持续数据源，替代推荐可能推"将死之料"
- **所属模块**：数据层 + 替代料智能体（ai/agents/alternatives.py）
- **严重程度**：中等
- **影响范围**：替代推荐的正确性与信任
- **发现依据**：模型有 lifecycle_status 字段（`api/models/__init__.py:120`），EOL 红线过滤已实现（`ai/agents/alternatives.py:254-257`），但全项目无 EOL/PCN 数据获取管道（无原厂通知接入、无第三方生命周期数据源对接的证据）；替代数据 metadata 的 source_types 含"LLM 推理"（`data/alternatives/alternatives.json`），该来源无法提供时效性生命周期信息；对立证据：Supplyframe DSI 实时生命周期、Sourcengine 交期报告、智芯谷停产预警
- **问题描述**：替代推荐最致命的错误是"推荐了一个也停产/即将停产的料"。过滤逻辑已写好，但没有持续更新的 lifecycle 数据源，红线机制形同虚设——字段大概率停留在默认值 active/unknown。
- **可能后果**：推荐的替代料同样缺货/停产，用户按建议改版后二次踩坑；此类事故对"可信决策支持"定位是毁灭性的。
- **推荐解决方案**：(1) 接入可获得的生命周期数据源：Nexar API（国际料）返回 lifecycle 状态、立创等平台的停产标注（官方 API 字段）；(2) 对 36 组替代关系逐组人工标注当前 lifecycle 并记录核验日期；(3) 推荐输出中强制展示"生命周期状态+数据时间"，unknown 时明示"未核验"。
- **修改成本**：低-中
- **优先级**：P1
- **是否影响当前上线**：部分（不影响功能演示，影响推荐可信度）
- **是否需要重构**：否
- **验收标准**：替代库 100% 组别有 lifecycle 标注与核验日期；推荐输出必含生命周期字段与数据时间；抽检 30 组推荐，无"推荐 EOL 料且未标注"的情况。

### 问题 9：行业研究文档对头号竞品营收数据严重失真（112.3 亿 vs 实际 25.77 亿）
- **所属模块**：docs/ 战略研究资产
- **严重程度**：严重
- **影响范围**：战略判断、资源分配、对外融资材料可信度
- **发现依据**：`docs/电脑制作全链路产业链分析.md:492` 称"云汉芯城 2024 年营收 112.3 亿人民币"；招股书口径 2024 年主营业务收入 25.77 亿元（[readtheone IPO 数据](https://www.readtheone.com/ipos/301563)，与发行文件一致）；2026Q1 营收也仅 11.49 亿（同花顺）
- **问题描述**：项目知识库中头号竞品的体量被高估约 4.4 倍，且该文档被明确用作"数据库建设和产业研究参考"。失真数据会直接污染：市场规模测算、竞对威胁评估、融资 BP 中的竞争页。
- **可能后果**：基于错误体量做出过度悲观/乐观的决策（例如误以为云汉覆盖面是实际 4 倍而不敢切入其未覆盖的缝隙）；对外材料被专业投资人当场证伪，损害团队可信度。
- **推荐解决方案**：(1) 立即修正该条目为招股书口径（25.77 亿元，2024），并补充 2023 年 26.37 亿、2022 年 43.33 亿的趋势（反映行业周期）；(2) 对该文档所有标"行业知识/待验证"及第三方市场站点来源的数字建立复核清单；(3) 建立竞品数据的一手来源规则：上市公司以招股书/年报为准，未上市公司标注"未经审计"。
- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：文档修正完成并注明来源与修正日期；文档内所有竞品财务数字均可溯源到一手来源或被标注【未经审计】；新增竞品（猎芯/硬之城/华强电子网/芯查查/智芯谷/Supplyframe XQ）进入监测清单。

### 问题 10：目标市场与竞品主战场正面重叠，未找到结构性缝隙
- **所属模块**：战略/市场选择
- **严重程度**：中等
- **影响范围**：获客成本、生存空间
- **发现依据**：PRD 画像为"深圳 30-200 人中小硬件制造商/EMS"（`docs/AI供需对接平台-产品需求文档.md:79`）；云汉核心定位即"中小批量小散临急"（全景网答复）、立创基本盘即中小批量与工程师（搜狐 2022-08）；华强电子网覆盖华强北中小商户生态；PRD 场景一"缺货找替代"（:93-101）与云汉芯应急、猎芯现货在库、硬之城 BOM 报价直接撞车
- **问题描述**：项目选择的用户与场景正是所有直接竞品投入最重的主战场。竞品在该场景用"自营现货+即时成交"服务，MatchForge 用"信息撮合+建议"服务，同一用户同一痛点下体验代差明显。结构性缝隙（竞品服务不到的）尚未被识别和验证。
- **可能后果**：获客时用户第一反应是"为什么不用立创/云汉"；在无 10 倍好的单点场景前，转化率与留存都会被压制。
- **推荐解决方案**：验证并聚焦 1-2 个结构性缝隙，候选（需访谈验证）：(1) **国产替代验证决策**——国产料参数/质量不透明、验证周期长（产业链分析:535 已指出），竞品的推荐不做"敢不敢换"的论证，MatchForge 的决策支持定位恰好覆盖；(2) **多平台比价整合**——采购要在立创/云汉/猎芯/华强北之间来回查（产业链分析:536 已指出数据分散），MatchForge 做"一次询价、多源聚合"的中立层（不自营、不站队，恰是自营竞品做不了的）；(3) **缺货预警前置**——在客户 BOM 设计阶段就介入风险扫描（对标 Supplyframe DSI 的设计期介入）。
- **修改成本**：低（定位与访谈工作，非开发）
- **优先级**：P1
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：完成 ≥10 个画像用户访谈，验证至少 1 个缝隙场景的付费/留存信号（如"愿为国产替代决策报告付费"或"愿持续使用多源比价"）；PRD 更新明确主攻缝隙场景与"为什么不与立创/云汉正面竞争"的一页纸回答。

### 问题 11：获客与留存通道无设计，竞品均有低成本流量入口
- **所属模块**：增长/运营
- **严重程度**：中等
- **影响范围**：冷启动、获客成本
- **发现依据**：项目内无官网/内容/社区/工具引流等获客通道的任何证据（仅 PRD:636 提及"人工 BD 首批"）；对立证据：嘉立创 EDA 免费+大学计划+免费物料（官网）、Octopart 700 万次/月搜索流量、Supplyframe 免费 ECAD 模型 100 万注册用户+Wevolver 内容社区、立创社区/开源硬件
- **问题描述**：竞品的获客飞轮都是"免费工具/内容→流量→交易/变现"。MatchForge 只有"人工 BD 首批"（PRD:636），无任何可规模化的获客通道设计。AI 寻源助手本身是工具，理论上可以复用"免费工具引流"逻辑，但当前无落地。
- **可能后果**：冷启动依赖创始人 BD 人脉，无法复制；增长停滞在首批试点客户。
- **推荐解决方案**：(1) 把"免费替代查询（每日限次）"本身作为引流工具公开运营，SEO/内容围绕"XX 料缺货替代"长尾词（对标 Octopart 的料号 SEO 与 Findchips 博客）；(2) 输出内容资产：季度《国产替代与缺货情报简报》（对标 Sourcengine Lead Time Report），建立专业心智；(3) 进工程师社区（立创开源硬件、电子发烧友等）做工具植入与案例内容。
- **修改成本**：低-中
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：上线一个可公开访问的免费查询入口（带限次与注册转化）；发布首期情报简报并记录订阅数；3 个月内自然流量（非 BD）占新用户比例 ≥20%（埋点可证）。

### 问题 12：企业级能力与权限体系单薄，制约向中型 EMS/品牌客户上行
- **所属模块**：后端（api/auth.py、api/models）+ 产品
- **严重程度**：中等
- **影响范围**：客单价提升、企业试点签约
- **发现依据**：项目存在基础 auth（`api/auth.py`），但未检索到多角色组织、审批流、子账号、审计日志、ERP/采购系统集成的任何证据；对立证据：京东工业太璞（商品/采购/履约/运营全链路企业方案）、Supplyframe DirectSource（企业采购 SaaS，+250% YoY）、1688 企业采购体系
- **问题描述**：画像用户是 30-200 人企业（PRD:79），采购场景天然涉及"采购员发起→主管审批→多人协作"，且客户会要求与内部 ERP/审批流对接。当前单用户工具形态无法承接团队级使用。
- **可能后果**：试点只能服务单个采购员个人效率，无法签企业级合同；SaaS 订阅定价上不去（个人工具 vs 团队系统价差 10 倍）。
- **推荐解决方案**：MVP 阶段做最小企业化：(1) 组织-成员两级模型（公司实体+成员账号），RFQ 与询价记录归属组织；(2) 询价单"发起→确认"一步审批流（不做复杂 OA）；(3) 导出/接口预留（Excel 导出+只读 API，见问题 6）。明确不做：完整 OA、ERP 深度集成（超出 MVP）。
- **修改成本**：中
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：部分（用户模型需加组织维度，建议尽早做以免后期迁移）
- **验收标准**：支持一个组织下 ≥3 个成员账号，数据按组织隔离；RFQ 有发起/确认两态；试点客户中至少 1 家以团队（≥2 账号）形式使用。

### 问题 13：替代数据 metadata 自相矛盾（自称 30 组、实际 36 组），数据治理粗放影响对外专业可信度
- **所属模块**：数据治理（data/alternatives/alternatives.json）
- **严重程度**：轻微
- **影响范围**：数据可信度、对外合作展示
- **发现依据**：`data/alternatives/alternatives.json` metadata 字段 `total_groups: 30`，实测 groups 数组长度为 36；同文件 `generated: 2026-07-14` 与 `updated_at: 2026-07-14` 但版本号 2.0 无变更记录；source_types 混含"Datasheet 交叉引用/行业交叉表/LLM 推理"三类可信度差异极大的来源，未逐组区分
- **问题描述**：对外（供应商/投资人/试点客户）展示数据资产时，metadata 与实际不符会被当场发现；"LLM 推理"来源未逐组标注，使高可信的 Datasheet 交叉引用与低可信的 LLM 推测混杂，整体可信度被拉低。
- **可能后果**：专业合作方质疑数据严谨性；无法回答"哪些替代是 Datasheet 级、哪些是 AI 推测"。
- **推荐解决方案**：(1) 修正 metadata 并建立生成脚本自动统计（杜绝手填）；(2) 每组替代增加 source_type 单值字段与证据链接；(3) 前台展示时按来源分级标注（如"Datasheet 核验/行业交叉表/AI 推测-待验证"）。
- **修改成本**：低
- **优先级**：P3
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：metadata 统计由脚本生成且与实际一致；每组替代有单一 source_type 与证据；前台推荐按来源分级展示。

## 4. 领域评分

### 评分一：竞争定位与差异化清晰度 —— 4 / 10

**依据**：定位收窄决策（PRD:20）本身正确且及时（+），"工具先行、不碰交易"的边界意识与表述红线（PRD:60-64）显示风控成熟（+），单边工具+窄品类冷启动符合平台演进规律（+）。但：核心差异化"AI 替代推荐"已被云汉 HiBOM、硬之城、猎芯、智芯谷、Supplyframe XQ 变成标配（-2）；目标市场与竞品主战场正面重叠、未验证结构性缝隙（问题 10，-2）；闭环在 RFQ 处断裂导致"推荐≠可买"，与自家产业链分析 9.2 链路矛盾（问题 2，-2）。

### 评分二：相对竞品的商业可行性（数据/壁垒/模式） —— 3 / 10

**依据**：数据规模落后 4-5 个数量级且补数路径有合规风险（问题 1）；可信度基础设施空白而竞品均有质检/担保/审核体系（问题 4）；唯一变现假设未验证、无落地备选（问题 3）；无流量入口与 API 生态（问题 6、11）；且最关键的护城河要素（供应商网络、真实交易数据、品牌流量）均属于"短期无法通过开发解决"的类别（1.5 节）。保留 3 分是因为：策略方向（先工具后平台、中立撮合、决策支持）在逻辑上仍有一条可验证的窄路，且竞品的 AI 全链路对话体验普遍薄弱，存在体验代差窗口——但窗口正在被云汉 HiBOM 等产品压缩，预计以季度计。
