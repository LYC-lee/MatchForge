# 前端工程审计报告

审计范围：`web/src` 全部（views/、components/、stores/、api/、router/、composables/、mock/、types/）及 `web/package.json`、`vite.config.ts`、`tsconfig*.json`、`web/dist` 构建产物。审计方式为静态代码阅读 + 构建产物测量，未运行动态 E2E。

## 1. 领域概述

**真实实现情况：**

- **技术栈与构建**：Vue 3.5 + TS 6.0 + Pinia 3 + Vue Router 4 + Vite 8（`web/package.json:11-28`）。全部视图组件使用路由级 `import()` 懒加载（`web/src/router/index.ts:6-30`），构建产物 JS 总体积极小（`dist/assets` 中 `index-*.js` 仅 56K，axios 48K，按路由拆包正常）。dist 总 14MB，其中约 13MB 为 `public/assets` 下的 8 张 PNG 落地页图片（单张 1.3–1.8MB，实测 `web/public/assets/`）。
- **视图与路由**：28 条路由，含 landing/login/register 公开页与 requiresAuth 业务页（采购方驾驶舱、BOM、缺件采购、AI 寻源对话、企业问答、供应商工作台三页、管理两页）。路由守卫统一校验会话（`web/src/router/index.ts:38-45`）。
- **状态管理**：Pinia 两个 store。`stores/auth.ts`（238 行）负责登录/注册/demo 登录/会话校验；`stores/procure.ts`（636 行）是寻源工作流核心状态机，覆盖 SSE 流式事件（token/progress/citation/result/error）、多轮对话快照回传、供应商选择、历史会话恢复，职责较重但逻辑完整、注释充分。
- **API 层**：存在统一 axios 实例（`web/src/api/index.ts:16-20`），带请求拦截注入 Bearer、响应拦截 401 刷新队列与统一错误归一化（`normalizeError`，行 139-171）。`api/enterprise.ts`（522 行）、`api/kb.ts`（209 行）、`api/demo.ts`（336 行）均复用该实例（均有 "复用 axios 实例" 注释）。**但** `api/procure.ts` 与 `stores/auth.ts` 使用裸 axios，`api/sse.ts` 用裸 fetch，绕开了统一封装（见问题 1）。
- **SSE 自研解析**：`api/sse.ts`（106 行）用 fetch + ReadableStream 手解 `text/event-stream`（因寻源接口是 POST），有解析失败阈值（MAX_PARSE_FAILURES=3，行 33）、心跳帧兼容、AbortController 断流，质量较好。
- **XSS 防护**：全站仅 1 处 `v-html`（`components/chat/MarkdownContent.vue:122`），且做了 `markdown-it html:false` + DOMPurify sanitize 双保险（行 46-50、94），链接统一 `rel="noopener noreferrer"`（行 71-75），是正面实践。
- **类型**：`types/procure.ts`（185 行）、`types/enterprise.ts`（100 行）定义了核心领域类型；tsconfig 继承 `@vue/tsconfig` strict 系配置并开启 `noUnusedLocals` 等（`tsconfig.app.json`）。但业务代码中 `any` 出现 67 处（含 store 核心字段 `alternatives = ref<any[]>`，`stores/procure.ts:62-63`）。
- **mock 体系**：`src/mock/`（dashboardAdapter.ts、enterpriseContext.ts、data.ts、sse.ts）仍被生产 composable `useDashboard.ts` 直接引用并作为运行时降级数据源。
- **测试**：`web/` 下无任何单元/E2E 测试，package.json 无 test 脚本；`tests/` 目录全部为后端 pytest。

## 2. 问题清单

### 问题 1：寻源核心链路（SSE + 会话历史）不携带认证 Token，绕开统一 API 封装
- 所属模块：api/sse.ts、api/procure.ts
- 严重程度：严重（若后端对 `/procure/stream`、`/procure/sessions` 启用鉴权则升级为致命）
- 影响范围：AI 寻源主流程（发起寻源、确认规格、重新生成 RFQ、重试匹配）、历史会话列表/详情/删除
- 发现依据：`web/src/api/sse.ts:14-22`（fetch 请求头只有 Content-Type/Accept，无 Authorization）；`web/src/api/procure.ts:23-34`（调用 fetchSSE 前未注入 token）；`web/src/api/procure.ts:49-71`（fetchSessions/fetchSessionDetail/deleteSessionApi 用裸 axios，无拦截器、无 token、无 401 处理）；对比 `web/src/api/index.ts:25-35`（统一实例的 token 注入逻辑）
- 问题描述：统一 axios 实例具备完整的 token 注入与 401 处理，但项目最核心的寻源 SSE 与会话历史两条链路均未复用它。SSE 因 POST + 流式无法直接用 axios 可以理解，但应手动从 auth store 取 token 放进 fetch headers；会话历史三个接口则完全没有理由用裸 axios。
- 可能后果：后端一旦开启接口鉴权，寻源主流程全量 401 且无自动重登录/刷新处理；当前阶段等于核心写接口（stream 触发 LLM 调用，有成本）对外无身份校验，存在被匿名刷接口的风险。`user_id` 由前端 localStorage 自报（`composables/useHistory.ts:12-27`），无 token 绑定时可被伪造拉取他人会话。
- 推荐解决方案：fetchSSE 增加可选 headers 参数，streamProcure 从 `useAuthStore().token` 注入 `Authorization: Bearer`；fetchSessions 等三个函数改为复用 `@/api` 实例；后端配合校验 token 与 user_id 一致性（后端域配合项）。
- 修改成本：低
- 优先级：P0
- 是否影响当前上线：是
- 是否需要重构：否（局部补齐）
- 验收标准：寻源 SSE 请求与 sessions 请求在网络面板中携带 Authorization 头；无 token 时后端返回 401 且前端跳转登录；抓包验证伪造 user_id 无法拉取他人会话。

### 问题 2：权限控制仅停留在"是否登录"，无角色级路由与菜单控制；管理页对所有登录用户开放
- 所属模块：router、components/layout
- 严重程度：严重
- 影响范围：`/admin/knowledge`、`/admin/audit`、`/supplier/*` 三类页面；导航栏
- 发现依据：`web/src/router/index.ts:15,26,28-30`（管理/供应商路由 meta 只有 `requiresAuth: true`，无角色字段）；`web/src/router/index.ts:38-45`（守卫只调 `auth.validateSession()`）；`web/src/components/layout/AppHeader.vue:14-23`（mainNav 对所有人渲染"数据与知识库""供应商工作台"等全部入口，无 role 过滤）
- 问题描述：`AuthUser.role` 已定义 buyer/supplier/admin/member/enterprise_admin/platform_admin（`stores/auth.ts:19`），但前端无任何一处基于 role 的路由或菜单判断。普通 member 登录后可直接看到并进入管理页与供应商工作台。
- 可能后果：越权访问管理界面；即使后端接口拒绝写操作，管理页数据结构、租户信息也可能被非授权用户浏览；供应商/采购方双视角混在同一导航造成误操作。
- 推荐解决方案：路由 meta 增加 `roles?: string[]`，守卫中校验 `auth.user?.role`；AppHeader mainNav 按 role 过滤（如供应商只看到 `/supplier/*`）；后端必须做服务端鉴权兜底（前端控制只是 UX 层）。
- 修改成本：低
- 优先级：P0
- 是否影响当前上线：是
- 是否需要重构：否
- 验收标准：以 member 角色登录，直接访问 `/admin/audit` 被重定向且无对应菜单项；以 supplier 登录仅见供应商导航；后端越权请求返回 403（需后端域确认）。

### 问题 3：Token 明文存 localStorage，且 401 刷新机制是死代码
- 所属模块：stores/auth.ts、api/index.ts
- 严重程度：中等（原型→MVP 阶段可接受，但需列入上线前安全清单）
- 影响范围：全站会话安全
- 发现依据：`web/src/stores/auth.ts:200-209`（`persistSession` 将 token + expiresAt 写入 `localStorage['matchforge:session']`）；`web/src/api/index.ts:121-127`（`doRefresh()` 注释"后端暂未提供 /auth/refresh 接口"，恒 `return false`，上方 94 行刷新队列/重放逻辑永远不会成功）
- 问题描述：localStorage token 可被任意 XSS 载荷窃取（当前 DOMPurify 已大幅收敛 XSS 面，风险可控但不为零）；8 小时 TTL（`auth.ts:28`）到期后无刷新机制，401 拦截器中的刷新-重放管线（行 86-119）是完整的死代码，误导后续维护者。
- 可能后果：XSS 一旦出现即丢会话；token 过期用户体验为"操作中突然失败跳登录"；维护者误以为有刷新能力。
- 推荐解决方案：MVP 阶段可保留 localStorage，但应：1) 删除或显式标注死代码（401 直接 logout 跳登录）；2) 上线前评估迁移 httpOnly Cookie + CSRF token；3) 后端补 `/auth/refresh` 或缩短 token TTL 并提前静默续期。
- 修改成本：低（清理死代码）/中（Cookie 化）
- 优先级：P1
- 是否影响当前上线：否（安全清单项）
- 是否需要重构：否
- 验收标准：代码中不存在永远不会成功的刷新路径；安全清单中明确记录 token 存储方案与改进计划。

### 问题 4：mock 数据残留混入生产运行路径，后端故障时用户无感知地看假数据
- 所属模块：composables/useDashboard.ts、mock/
- 严重程度：严重
- 影响范围：经营驾驶舱（/app，登录后首页）
- 发现依据：`web/src/composables/useDashboard.ts:12-14`（生产 composable 直接 import `@/mock/dashboardAdapter`、`@/mock/enterpriseContext`）；行 203-215（catch 后 `dataSource = 'mock'` 并渲染 mock dashboard，仅在 error 文案中提示"已降级到 mock 数据"）；行 259-263（导出 `useMockInternalQuestions` 供旧视图）；对照 `web/.env.example` 注释"所有功能已对接真实后端 API，无需 mock 模式"（与实际矛盾）；`src/mock/` 四文件合计约 900 行
- 问题描述：驾驶舱是登录后首屏，后端任一接口异常即静默切换为内置假数据（订单、缺件、预测全是编造的），且 AppHeader 的数据来源标签只区分 api/empty/loading（`AppHeader.vue:27-29`），mock 状态显示为"暂无数据"，用户无法区分"真没数据"和"在看演示数据"。
- 可能后果：真实客户在后端故障时基于虚构订单/缺件数据做采购决策，业务事故级风险；也掩盖了后端可用性监控信号。
- 推荐解决方案：非 demo 账号禁用 mock 降级，改为显式错误态 + 重试按钮；`is_demo` 场景保留 mock 但 UI 明显水印"演示数据"；删除或收敛 `src/mock/` 到 demo 专用入口；修正 .env.example 描述。
- 修改成本：低
- 优先级：P1
- 是否影响当前上线：是
- 是否需要重构：否
- 验收标准：断开后端后以非 demo 账号访问 /app，页面显示明确错误而非 mock 数据；mock 相关 import 不出现在非 demo 代码路径。

### 问题 6：procure store 中四段 SSE 回调编排高度重复（约 320 行可复制代码）
- 所属模块：stores/procure.ts
- 严重程度：中等
- 影响范围：寻源状态机维护性
- 发现依据：`web/src/stores/procure.ts:213-288`（startProcure）、`291-371`（confirmSpec）、`412-453`（regenerateRfq）、`456-503`（retryMatch）——四个函数各自内联完整的 onStart/onToken/onProgress/onCitation/onError/onParseError/onResult/onEnd 回调对象，其中 onError/onParseError/onResult/onEnd 与大部分 onToken 逻辑几乎逐行相同
- 问题描述：同一套流式事件处理协议被复制 4 份，仅 agent 分支细节不同。任何协议变更（如新增事件类型）需同步改 4 处，已出现漂移迹象（startProcure 的 onToken 有 shouldAcceptChatToken 过滤，confirmSpec 的 onToken 直接拼 rfqDoc——这是有意的，但 onError 中 phase 处理已开始不一致）。
- 可能后果：修 bug 漏改某一分支；协议演进时行为分叉。
- 推荐解决方案：抽出 `makeStreamHandlers(overrides)` 工厂，公共回调一份，差异通过参数注入（如 token 目标：chatBuffer | rfqDoc）。
- 修改成本：中
- 优先级：P2
- 是否影响当前上线：否
- 是否需要重构：是（局部）
- 验收标准：四类流式入口共享同一份基础 handler；store 行数下降 150+ 行；四条路径手工回归通过。

- 是否需要重构：否
- 验收标准：`npm run test` 可运行且覆盖上述三个模块的关键分支；CI 中执行。

### 问题 10：供应商对比表在模板中重复执行 O(n) filter；长列表无虚拟化
- 所属模块：components/procure/SuppliersMatch.vue
- 严重程度：轻微
- 影响范围：供应商匹配卡片（数据量大时）
- 发现依据：`web/src/components/procure/SuppliersMatch.vue:191-234`（对比表每一行都写 `suppliers.filter((x) => compareIds.has(x.id))`，单次渲染重复计算 9 次）；行 267（`v-for="s in filteredSuppliers"` 全量渲染，无分页/虚拟滚动）
- 问题描述：对比表每行 filter 应提取为一个 computed；供应商列表目前全量渲染，MVP 数据量（几十家）无感，但品类放开到数百家时 DOM 节点线性膨胀。
- 可能后果：数据量增长后页面卡顿；重复 filter 造成不必要的重渲染开销。
- 推荐解决方案：新增 `comparedSuppliers` computed 供对比表循环；列表超过 ~100 项时引入简单分页或 `vue-virtual-scroller`（MVP 可先加分页）。
- 修改成本：低
- 优先级：P3
- 是否影响当前上线：否
- 是否需要重构：否
- 验收标准：对比表模板中不再出现 filter 调用；200 家供应商时滚动与筛选流畅。

### 问题 11：历史记录双轨存储（API + localStorage 全量快照）存在一致性与配额风险
- 所属模块：composables/useHistory.ts、views/ChatView.vue
- 严重程度：中等
- 影响范围：历史会话功能
- 发现依据：`web/src/composables/useHistory.ts:82-115`（load 合并 API 与 localStorage 两源，仅以 thread_id 去重，无 updated_at 冲突裁决）；行 164-196（saveToLocal 把完整 state + messages 快照塞 localStorage，100 条上限，配额超限时砍半重试）；`ChatView.vue` 保存 messages 含全部卡片 payload
- 问题描述：同一会话可能在两端数据不同步（如 API 成功但本地旧快照残留），合并逻辑无条件 API 优先但不清理本地孤儿记录；单条会话快照（含 RFQ 全文、供应商列表）可达数十 KB，100 条逼近 localStorage 5MB 配额，已有砍半兜底说明实际踩过坑。
- 可能后果：历史列表出现重复/过期会话；极端情况下写入静默失败丢历史。
- 推荐解决方案：明确 localStorage 仅为"匿名/后端不可用"场景的降级存储，登录用户以 API 为唯一事实源，加载成功后清理对应本地记录；快照裁剪（卡片 payload 不存 ui 临时字段）。
- 修改成本：低
- 优先级：P2
- 是否影响当前上线：否
- 是否需要重构：否
- 验收标准：登录用户连续创建 5 个会话后，localStorage 中不再保留对应冗余快照；两源合并无重复条目。

### 问题 12：API 层类型完整度不足，核心实体在 store 中退化为 any
- 所属模块：stores/procure.ts、types/
- 严重程度：轻微
- 影响范围：寻源域类型安全
- 发现依据：`web/src/stores/procure.ts:62-63`（`alternatives = ref<any[]>`、`matchedSuppliers = ref<any[]>`，尽管 types/procure.ts 已定义 Alternative/Supplier）；全仓 `any` 67 处（grep 实测）；`useHistory.ts:37-39`（`state: any`、`messages?: any[]`）
- 问题描述：类型定义存在但未被 store 采用，重构时编译器无法护航；applyState 对后端 state 各字段直接 `as` 断言（`stores/procure.ts:139-166`），无运行时校验。
- 可能后果：后端字段变更时前端静默错位（如 alternatives 结构变化只在运行时炸）。
- 推荐解决方案：store 字段改用已定义的 Alternative/Supplier/LeadGrade 类型；applyState 入口处加一个轻量校验函数（手写 guard 即可，不必引入 zod）。
- 修改成本：低
- 优先级：P3
- 是否影响当前上线：否
- 是否需要重构：否
- 验收标准：stores/procure.ts 中无 `any[]` 核心字段；tsc 严格模式通过。

### 问题 13：开发环境与构建配置存在小坑（HMR 关闭、无环境变量体系）
- 所属模块：vite.config.ts、环境配置
- 严重程度：轻微
- 影响范围：开发体验、部署灵活性
- 发现依据：`web/vite.config.ts:15`（`hmr: false`，改代码需手动刷新）；`.env.example` 全文仅两行注释，无任何 `VITE_*` 变量；baseURL `/api/v1` 硬编码于 `api/index.ts:17`，dev 靠 proxy（vite.config.ts:16-21），生产依赖同源反代
- 问题描述：hmr:false 通常是为规避 SSE/代理问题的权宜设置，应记录原因；无环境变量体系意味着 staging/生产 API 地址切换只能改代码或靠 nginx 同源。
- 可能后果：开发效率损失；多环境部署时配置漂移。

- 修改成本：低
- 优先级：P3
- 是否影响当前上线：否
- 是否需要重构：否
- 验收标准：.env.example 列出全部可用变量；hmr 设置有注释说明。
