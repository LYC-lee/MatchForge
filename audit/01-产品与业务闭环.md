## 1. 领域概述

### 1.1 文档宣称的产品定位（三份文档内部一致）

- PRD（`docs/AI供需对接平台-产品需求文档.md:20-28`）明确：首期**不是平台**，是"单边采购寻源工具"——采购输入型号或自然语言，系统识别规格、推荐替代料、匹配候选供应商、生成可编辑询价单。
- 远期双边平台愿景（上游线索付费、撮合）被 PRD 显式排除在首期之外（`docs/AI供需对接平台-产品需求文档.md:66-67`）。
- 非目标（`docs/AI供需对接平台-产品需求文档.md:57-63`）：不做在线交易、支付、完整供应商 CRM、BOM 批量优化、实时库存承诺。
- README（`README.md:3-5`）口径与 PRD 不一致，自称"AI 供需对接平台"，并宣称"分级线索推给上游"的完整闭环。【已确认事实】

### 1.2 代码实际实现的产品（三套产品并存）

【已确认事实】代码中实际存在三条互相独立的产品线：

1. **AI 寻源对话工具**（与 PRD 对齐）：`web/src/views/ChatView.vue`（1163 行）+ `web/src/views/ProcureView.vue` + `POST /api/v1/procure/stream`（`api/routers/procure.py:68`）+ LangGraph 8 节点链 `chat → parse → normalize → alternatives → match → rag_enrich → gen_rfq → grade`（`ai/supervisor.py:80`）。
2. **企业经营驾驶舱 + 缺件采购闭环**（PRD 外产物，继承自"电脑元件客服 MVP"）：`HomeView.vue`（经营驾驶舱）、`ProductsBomView.vue`（产品与 BOM）、`ShortageProcurementView.vue`（缺件与采购），后端 `api/routers/dashboard.py`（BOM/订单/预测/缺件/推荐动作，共 8 个端点）。
3. **企业级 RFQ/报价双边闭环**（PRD 外产物）：`POST /rfqs`、`POST /rfqs/{id}/send`、`POST /rfqs/{id}/quotations`、`GET /rfqs/{id}/quote-comparison`（`api/routers/rfqs.py:183,269,349,439`）+ 供应商工作台三页（`web/src/views/supplier/SupplierDashboard.vue`、`SupplierLeads.vue`、`SupplierProducts.vue`）+ 线索查看/拒绝（`api/routers/supplier_leads.py:69,95,110`）。

另有一套**演示沙盘**（`api/routers/demo.py`，18 个端点，操作 6 家主视角企业 9001-9006）和**企业知识库 RAG**（`CompanyChat.vue`、`CompanyAssistant.vue`、`AdminKnowledge.vue` + `chat.py`/`relationships.py`/`kb_admin.py`）。

## 2. 问题清单

### 问题 1：AI 询价单与线索分级不落库、不推上游——宣称闭环最后两环断裂

- **所属模块**：ai/agents/gen_rfq.py、ai/agents/grade.py、web/src/stores/procure.ts
- **严重程度**：致命
- **影响范围**：README 宣称的核心闭环（`README.md:5`）、"线索分级推给上游"的商业模式根基
- **发现依据**：`ai/agents/gen_rfq.py:80`（rfq_id 为内存生成 `MF-{date}-{uuid}`）；`ai/agents/grade.py:50`（lead_grade 仅写入 state）；`api/routers/procure.py:90-99`（SSE 结束后无持久化调用）；`web/src/stores/procure.ts:408-410`（"标记已发送"只改 ref）；全仓 grep `lead_grade` 无 DB 写入点
- **问题描述**：用户跑完寻源链后得到的询价单只是 SSE 流里的一段文本，刷新即失（仅存 localStorage）；线索分级结果只展示给采购商本人，上游供应商永远收不到这条"A 级线索"。
- **可能后果**：对外宣称的闭环在演示后无法兑现；试点客户无法复用历史询价；商业化（卖线索）无数据载体。
- **推荐解决方案**：在 `/procure/stream` 的 `end` 事件前将 `rfq_doc + parsed_spec + matched_suppliers + lead_grade` 写入 `rfqs` 表（可复用 `RfqRecord` 或新增 `ai_rfqs` 表），`lead_grade` 落 `RfqSupplierLink.match_score/match_reason`；前端"发送"按钮改调 `POST /rfqs` + `POST /rfqs/{id}/send`。
- **修改成本**：中
- **优先级**：P0
- **是否影响当前上线**：是（若上线即宣称闭环）
- **是否需要重构**：否（新增写入点即可）
- **验收标准**：完成一次 SSE 寻源后，数据库出现对应 RFQ 记录且供应商在其线索列表可见该线索，含分级分数；页面刷新后历史记录可完整回显。

### 问题 2：两套 RFQ 体系互相断开，用户从"AI 寻源"走不到"真实询价"

- **所属模块**：ai/agents/gen_rfq.py × api/routers/rfqs.py × web/src/views/ChatView.vue
- **严重程度**：致命
- **影响范围**：核心用户旅程（PRD §7 核心流程的最后一跳）
- **发现依据**：`rfqs.py:42-59` RfqCreate 要求手工填 buyer_company_id/title/part_number；ChatView/ProcureView 中无任何调用 `POST /rfqs` 的代码（grep `/rfqs` 仅 `web/src/api/enterprise.ts:356-400` 被驾驶舱侧 `useRfq` 使用）；`web/src/router/index.ts` 寻源页与缺件采购页互相无跳转
- **问题描述**：系统里同时存在"AI 生成的询价单文本"（内存态）和"企业 RFQ 记录"（DB 态、可发送收报价），两者字段、ID 体系、入口完全不同，没有打通。用户在 ChatView 里寻源完，想真正向匹配到的供应商询价，必须手工去另一个页面重填一遍。
- **可能后果**：核心卖点"10 分钟拿到替代建议+可直接发送的询价单"（PRD §5 成功标准）在真实使用中断裂；双边数据无法沉淀。
- **推荐解决方案**：以 DB 态 `RfqRecord` 为唯一事实源：AI 链的 gen_rfq 输出直接落库为 draft RFQ；ChatView 的供应商勾选写入 `supplier_candidates`；"发送"统一走 `POST /rfqs/{id}/send`。
- **修改成本**：中
- **优先级**：P0
- **是否影响当前上线**：是
- **是否需要重构**：局部重构（gen_rfq 输出契约 + 前端发送动作）
- **验收标准**：从 ChatView 输入需求到供应商在其工作台看到线索并报价，全程不离开会话、不重复填写任何字段。

### 问题 3：企业访问控制默认放行，任何注册用户可冒充任意买方/供应商

- **所属模块**：kb/auth.py、api/deps.py
- **严重程度**：致命（对双边业务而言）
- **影响范围**：所有以 company_id 为隔离边界的接口（rfqs、quotations、supplier_leads、companies、knowledge）
- **发现依据**：`kb/auth.py:227-241` `can_access_company`——"默认策略（无白名单记录）：允许……若该 user_id 在 kb_company_access 有任意记录才强制校验"；`api/deps.py:32-52` `check_company_access` 依赖该函数；`api/routers/rfqs.py:184` 创建 RFQ、`rfqs.py:349` 供应商报价均仅经此校验
- **问题描述**：注册时（`api/routers/auth.py:42-48`）用户自填公司名，系统不校验企业与账号的归属关系；只要账号没有任何白名单记录（新注册用户的默认状态），即可对任意 company_id 创建 RFQ、提交报价、查看线索。
- **可能后果**：试点阶段即出现"冒名询价/冒名报价"，双边信任崩塌；也无法支撑"供应商为线索付费"——无法证明线索被正确企业看到。
- **推荐解决方案**：注册时将用户与 enterprise/company 绑定写入 `kb_company_access`（默认deny-all，再显式授权）；企业归属需人工或凭证核验后才激活。
- **修改成本**：中
- **优先级**：P0
- **是否影响当前上线**：是（若允许真实注册）
- **是否需要重构**：否（改默认策略 + 注册流程补一步）
- **验收标准**：新注册用户访问非本企业 company_id 的任一接口返回 403；企业管理员可为成员授权。

### 问题 4：README/架构文档宣称"Milvus 供应商匹配"，实际未在业务路径使用

- **所属模块**：README.md、docs/AI供需对接平台-系统架构文档.md、ai/agents/match.py
- **严重程度**：严重
- **影响范围**：对外技术口径、尽调可信度、部署依赖（docker-compose 仍起 Milvus）
- **发现依据**：`README.md:27`"供应商匹配(Milvus)"；架构文档 §7.3 `product_embeddings` collection 设计；实际 `ai/agents/match.py:24,79` 用 `filter_suppliers_raw`（MySQL）+ `search_knowledge_base`（kb RAG）；`ai/tools/milvus_client.py` 仅被 `tests/test_tools.py:90` 与 `ai/tools/__init__.py:32` 引用，无任何 agent 调用
- **问题描述**：文档与实现对供应商匹配的核心技术路径描述不一致。同理，架构文档 §6.1 的 API 总览（`POST /api/v1/procure`、`/rfq/generate`、`/rfq/submit`、`/leads`、`/admin/metrics`、`/suppliers/onboard`）与实际路由（`/procure/stream|spec|match`，其余均不存在）大面积不符（`api/routers/procure.py:37,68` vs 文档）。
- **可能后果**：技术尽调或客户 POC 时被当场戳穿；运维白扛 Milvus+etcd+minio 三个容器的资源与故障面。
- **推荐解决方案**：二选一——(a) MVP 阶段如实改文档：供应商匹配 = MySQL 规则 + RAG，Milvus 仅服务知识库分块（需核实 kb 是否实际使用 Milvus）；下线闲置 Milvus 依赖或标注"预留"。(b) 若供应商规模将上千，再把向量召回接回 match agent。
- **修改成本**：低（改文档）/ 中（改代码）
- **优先级**：P1
- **是否影响当前上线**：否（影响对外口径）
- **是否需要重构**：否
- **验收标准**：README、架构文档、实际代码三方对"供应商匹配用什么、有哪些 API"描述一致；未使用的基础设施在部署清单中显式标注。

### 问题 5：PRD F9"低置信替代料进人工审核队列"未实现，审核对象缺替代料

- **所属模块**：api/routers/audit.py、ai/agents/alternatives.py、web/src/views/P7AdminAudit.vue
- **严重程度**：严重
- **影响范围**：AI 安全红线的落地（PRD §13"低置信进人工审核"）、错误替代率≤5% 的核心安全指标
- **发现依据**：`api/routers/audit.py:9` 审核对象仅 `supplier_capability / rfq_supplier_match / quotation_anomaly`；`kb/models.py:595` 同；`ai/agents/alternatives.py` 低置信结果仅打标（`source=llm_inferred`、`verified=false`），全仓 grep 无任何向 `AuditQueueItem` 写入替代料的代码；P7AdminAudit.vue:71-79 的类型映射表亦无替代料
- **问题描述**：LLM 推理出的低置信替代料直接经 SSE 展示给用户（前端仅靠徽章提示），运营后台没有任何队列可以审核它们，PRD 设计的"置信度<0.7 进审核队列、前端折叠"的安全阀缺了队列这一半。
- **可能后果**：错误替代无人工拦截闸口；安全指标（错误替代率）无法度量也无法改进。
- **推荐解决方案**：alternatives agent 输出 `confidence<0.7 且 source=llm_inferred` 的条目时写入 `AuditQueueItem(item_type='alternative_review')`；审核页加对应类型；审核结果回写 Neo4j `verified` 属性。
- **修改成本**：中
- **优先级**：P1
- **是否影响当前上线**：是（涉及产品安全红线）
- **是否需要重构**：否
- **验收标准**：构造一条 LLM 推理低置信替代，审核队列出现对应待审项，审核"通过"后前端该条目标记变为"已核验"。

### 问题 6：供应商入驻与资质核验链路完全缺失

- **所属模块**：api/routers（无对应路由）、web/src/views（无入驻页）
- **严重程度**：严重
- **影响范围**：双边冷启动、PRD §16 MVP 的 Should 项"供应商入驻与资质核验"
- **发现依据**：架构文档 `docs/AI供需对接平台-系统架构文档.md:231` 设计了 `POST /api/v1/suppliers/onboard`（F7）与 `:233` `POST /admin/suppliers/{id}/audit`（F10）；实际 `api/routers/` 12 个文件中无 suppliers 路由、无 onboarding、无资质审核端点（`audit.py` 只审队列项）；注册接口 `api/routers/auth.py:21-26` 无供应商角色选项，`web/src/views/RegisterView.vue:19` 注释"供需角色由订单/RFQ/BOM/服务关系动态派生，不在注册时固化"
- **问题描述**：供应商数据只能由运营手工 curate 入库（35 家种子，`data/suppliers/suppliers.json`），供应商自己无法入驻、无法维护资料与资质，PRD 的"供应商自维护"数据来源不存在。
- **可能后果**：供给侧数据永远无法规模化、保鲜；"双边平台"只有双边账号壳，没有双边供给机制。
- **推荐解决方案**：MVP 阶段做最小入驻表单（公司名+品类+品牌+联系方式）进 `status=pending`，审核页增加"供应商入驻"类型；资质 OCR/第三方核验推迟。
- **修改成本**：中
- **优先级**：P1
- **是否影响当前上线**：否（影响试点扩张）
- **是否需要重构**：否
- **验收标准**：新供应商自助提交资料 → 出现在审核队列 → 审核通过后进入匹配候选池。

### 问题 7：产品定位漂移——PRD 非目标（驾驶舱/BOM/订单/预测/RAG 问答）占用大量页面与后端

- **严重程度**：严重

- **发现依据**：PRD 非目标 `docs/AI供需对接平台-产品需求文档.md:60` 明确不做"完整 BOM 批量优化"；实际 `api/routers/dashboard.py:31-100` 实现了 bom-summary/bom/orders/forecasts/shortages/recommended-actions/dashboard 8 个端点；`web/src/router/index.ts` 登录后首页 `/app` 是"经营驾驶舱"而非 AI 寻源；`CompanyChat.vue`（上下游协同问答 419 行）与 `CompanyAssistant.vue`（企业内部问答 327 行）在 PRD 页面清单（P1-P7）中不存在

### 问题 9：寻源接口与会话历史接口无鉴权，user_id 由客户端自报

- **所属模块**：api/routers/procure.py
- **严重程度**：严重
- **影响范围**：会话隐私、接口滥用（LLM 调用成本）
- **发现依据**：`api/routers/procure.py:68-114` `procure_stream` 无 `Depends(get_current_user)`，`user_id` 是请求体字段（`:47`，默认 anonymous）；`:201-210` `GET /procure/sessions?user_id=xxx` 同样无鉴权，可枚举任意 user_id 的会话列表；前端虽要求登录进 `/chat`（router requiresAuth），但 API 层完全开放
- **问题描述**：任何未登录者可调用 SSE 寻源（烧 LLM 额度）并遍历他人会话历史。

- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：是
- **是否需要重构**：否
- **验收标准**：无 token 调 `/procure/stream` 返回 401；A 用户无法读取 B 用户会话。

## 4. 领域评分

### 4.1 产品定位与闭环完整度：**4 / 10**

依据：
- 加分：PRD 本身定位清晰、克制（单边工具、明确非目标），AI 寻源主链 6 环中 4 环真实存在（输入/解析/替代/匹配），且有测试覆盖。
- 扣分：执行层定位漂移（PRD 非目标做成首页，问题 7）；宣称闭环最后两环断裂（问题 1、2）；文档与实现对核心技术路径口径不一（问题 4）；PRD 安全红线（低置信审核、反馈）缺半（问题 5、8）。

### 4.2 商业化与双边就绪度：**2 / 10**

依据：
- 加分：企业级 RFQ→线索→报价→对比的数据表与接口已存在（rfqs.py、supplier_leads.py），供应商工作台三页可用；demo 沙盘可演示双边叙事。
- 扣分：无供应商入驻（问题 6）、访问控制默认放行使双边流转不可信（问题 3）、无任何付费载体（全仓无 billing）、线索分级不落库（问题 1）、数据规模与壁垒不达标（问题 11）。"下游免费、上游线索付费"模式目前既无产品载体也无验证记录。

### 4.3 阶段判定：**可演示 Demo（接近、但未达到"可用 MVP"）**

判定依据（对照六级刻度）：
- 超出"概念验证/技术原型"：端到端 SSE 寻源链可运行、有真实种子数据与测试套件、有完整登录与驾驶舱界面。
- 达不到"可用 MVP"：核心闭环最后一跳（询价单真实发送给匹配供应商并收到报价）在 AI 主旅程上断裂（问题 1、2）；真实用户注册后权限边界不可信（问题 3）；PRD §17 的 MVP 验收指标无任何线上度量（问题 14）。
- 距"可试点"还差：问题 1/2/3/5/6 五个 P0-P1 项修复 + 一个品类的真实采购陪测（≥5 家真实买方跑通寻源→询价→供应商收到线索）。
- "可商业化"：当前无任何付费条件，且 PRD §18 自标最高风险假设"供应商愿为真实线索付费"未验证，不展开。

### 4.4 应删除 / 合并 / 推迟清单

**删除（低风险，立即）**：
- `api/routes/` 整目录（死代码，含假数据逻辑，问题 12）
- `web/src/views/demos/` 8 个全息 demo + `LoginHoloPro.vue`/`LoginWithHolo.vue`（问题 12）

**合并（P0-P1）**：
