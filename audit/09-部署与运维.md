## 1. 领域概述（该领域真实实现了什么、关键证据）

### 1.1 已实现的部分

**（1）基础设施一键编排——可用且质量尚可【已确认事实】**
`deploy/docker-compose.yml`（全文 238 行）定义了 7 个基础设施服务：MySQL 8.0（`docker-compose.yml:25-49`）、etcd v3.5.5（`:54-73`）、MinIO（`:79-99`）、Milvus v2.4.0 Standalone（`:105-132`）、Neo4j 5.20.0（`:138-161`）、PostgreSQL 16（`:167-186`）、Redis 7（`:192-207`）。正面事实：

`database/migrations/` 存在 6 个编号 SQL（02-07），均为非破坏式 `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN` 风格，头部有执行说明（如 `02_kb_schema.sql:1-11`、`07_user_name_company.sql:1-15`）。

## 2. 问题清单

### 问题 1：文档给出的后端启动命令必然失败（`uvicorn main:app` 双重错误）
- **所属模块**：文档 / 后端启动流程
- **严重程度**：致命
- **影响范围**：所有按文档操作的新开发者、任何新环境部署
- **发现依据**：`环境要求.txt:113` 写 `cd api && pip install -r requirements.txt && uvicorn main:app --reload`；而 `api/main.py:102` 实例名是 `main = create_app()`（模块内不存在 `app` 属性）；`api/main.py:110` 自举命令为 `uvicorn.run("api.main:main", ...)`；`api/main.py:52` `from kb.db import init_db` 与 `:56` `from api.routers import ...` 要求工作目录必须是项目根（在 `api/` 内启动会导致 `kb`、`api` 包不可导入）
- **问题描述**：文档命令有两处错误：① 应用对象名错误（`main:app`，应为 `main:main` 或更规范的 `api.main:main`）；② 工作目录错误（`cd api` 后顶层包 `kb`/`api` 无法导入）。按文档执行 100% 报 `Attribute "app" not found in module "main"` 或 `ModuleNotFoundError: No module named 'kb'`。
- **可能后果**：新开发者第一印象即"项目跑不起来"；试点部署/演示前夜才发现启动路径不通。
- **推荐解决方案**：将 `环境要求.txt:113` 改为在项目根执行 `pip install -r api/requirements.txt -r requirements-dev.txt && uvicorn api.main:main --reload`；同时在 README"快速开始"中同步。
- **修改成本**：低
- **优先级**：P0
- **是否影响当前上线**：是（新环境无法按文档上线）
- **是否需要重构**：否
- **验收标准**：全新机器/全新 venv 按修订后文档执行，`curl http://localhost:8000/api/v1/health` 返回 `{"status":"ok"}`。

### 问题 2：运行时必需依赖 `bcrypt` 未列入 `api/requirements.txt`
- **所属模块**：依赖管理 / 认证链路
- **严重程度**：致命
- **影响范围**：所有只按文档安装 `api/requirements.txt` 的环境（含未来生产部署）
- **发现依据**：`kb/auth.py:27` `import bcrypt`；启动链路 `api/main.py:56-57` → `api/routers/auth.py:9` `from kb.auth import login, ...` → 导入 `kb/auth.py`；`api/requirements.txt` 全文（34 行）无 `bcrypt`；`bcrypt` 仅出现在 `requirements-dev.txt:1`；`环境要求.txt` §8 启动步骤只字未提 `requirements-dev.txt`
- **问题描述**：按文档全新安装后，后端启动即 `ModuleNotFoundError: No module named 'bcrypt'`。当前开发机能跑只是因为开发者恰好装过 dev 依赖。
- **可能后果**：与问题 1 叠加，构成"clone 后永远起不来"的硬阻断；生产部署时同样炸。
- **推荐解决方案**：将 `bcrypt>=4.0` 移入 `api/requirements.txt`；并用一次"干净 venv 安装冒烟"作为验收（见问题 18 的 CI 建议）。
- **修改成本**：低
- **优先级**：P0
- **是否影响当前上线**：是
- **是否需要重构**：否
- **验收标准**：`python -m venv .venv && pip install -r api/requirements.txt && python -c "import api.main"` 无 ImportError。

### 问题 3：`.env.example` 空密码与 compose 硬编码密码冲突——照抄示例必连不上数据库
- **所属模块**：配置与密钥管理
- **严重程度**：严重
- **影响范围**：新开发者上手、环境一致性
- **发现依据**：compose 硬编码 `MYSQL_PASSWORD: matchforge123`（`docker-compose.yml:30-33`）、`NEO4J_AUTH: neo4j/matchforge123`（`:143`）、`POSTGRES_PASSWORD: matchforge123`（`:172-174`）、`redis-server --requirepass matchforge123`（`:196`）；而 `.env.example:40` `MYSQL_PASSWORD=`、`:52` `NEO4J_PASSWORD=`、`:58` `POSTGRES_PASSWORD=`、`:64` `REDIS_PASSWORD=` 全部留空；代码默认值为 `matchforge123`（`ai/config.py:52,67,91,99`）
- **问题描述**：python-dotenv 的语义是"键存在即取值"，空字符串会覆盖代码默认值（`os.getenv("MYSQL_PASSWORD","matchforge123")` 在 `.env` 含 `MYSQL_PASSWORD=` 时返回 `""` 而非默认值）。开发者按文档"复制 .env.example → 只填 DASHSCOPE_API_KEY"（`环境要求.txt:110`）后，MySQL/Neo4j/Redis/Postgres 全部以空密码连接，认证失败。
- **可能后果**：上手第三步即连锁报错，且报错点分散在四个组件、排查耗时；属于"文档引导用户走进坑里"。
- **推荐解决方案**：二选一——① `.env.example` 中直接写入与 compose 对齐的本地开发密码 `matchforge123` 并注释"仅限本地"；② compose 改为 `${MYSQL_PASSWORD:?required}` 变量插值并统一从根 `.env` 读取。MVP 阶段建议方案①，改动最小。
- **修改成本**：低
- **优先级**：P0
- **是否影响当前上线**：是
- **是否需要重构**：否
- **验收标准**：开发者复制 `.env.example` 仅填 LLM Key 后，`python api/db_init.py` 与后端启动均无认证错误。

### 问题 4：所有基础设施密码硬编码在 docker-compose.yml 中
- **所属模块**：配置与密钥管理
- **严重程度**：严重
- **影响范围**：仓库安全边界、未来任何共享/演示环境
- **发现依据**：`docker-compose.yml:30-33`（MySQL root/用户密码）、`:44`（healthcheck 内嵌 root 密码）、`:84-85`（MinIO `minioadmin/minioadmin123`）、`:117-118`（Milvus 引用 MinIO 密钥）、`:143`（Neo4j）、`:156`（healthcheck 内嵌密码）、`:172-174`（Postgres）、`:196` 与 `:202`（Redis 密码两处）
- **问题描述**：compose 文件已提交 git（`git ls-files` 可见），所有数据组件口令以明文固定在版本库中。MVP 本地开发可接受，但该文件会被直接拿去起演示/试点环境（`docs/...项目开发文档.md:164` 写明"MVP: 云容器服务"），且所有端口默认绑定 `0.0.0.0`（compose 未限制 bind 地址，如 `:35-36`、`:148-150`）。
- **可能后果**：一旦 compose 被用于云主机，MySQL/Neo4j/MinIO 控制台/Redis 以弱口令暴露公网，属典型拖库入口。
- **推荐解决方案**：compose 改为 `env_file: ../.env` + `${VAR}` 插值；演示/云环境部署时在 compose 中把端口绑定改为 `127.0.0.1:3306:3306` 形式或加防火墙说明；在 `环境要求.txt` 增加"对外部署前必须改密" checklist。
- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：本地演示否；任何对外部署是
- **是否需要重构**：否
- **验收标准**：compose 中 grep 不到明文密码；`docker compose config` 渲染后密码来自 `.env`；对外部署文档含端口绑定/改密说明。

### 问题 5：配置漂移——LLM 供应商、Postgres 库名、服务清单三方互不一致
- **所属模块**：配置管理 / 文档一致性
- **严重程度**：严重
- **影响范围**：上手可信度、Postgres 会话持久化功能
- **发现依据**：
  - LLM：`环境要求.txt:88-92` 写"通义千问 DashScope、`qwen-max`/`qwen-plus`、`text-embedding-v3`"；`.env.example:28-33` 与 `ai/config.py:22-37` 实际默认是火山方舟 `ark.cn-beijing.volces.com` + `glm-5.2` + `DeepSeek-V4-Flash` + SiliconFlow `BAAI/bge-m3`；变量名仍叫 `DASHSCOPE_API_KEY`（`ai/config.py:20`）却承载非 DashScope 服务；
  - Postgres 库名：compose 建库 `POSTGRES_DB: matchforge_memory`（`docker-compose.yml:174`），代码默认 `matchforge_memory`（`ai/config.py:68`），但 `.env.example:59` 写 `POSTGRES_DATABASE=matchforge`；
  - 服务清单：`环境要求.txt:66-72` 未列 Postgres，compose 却有（`:167-186`）；`:68` 写 Milvus 镜像 `v2.4-latest`，compose 固定 `v2.4.0`（`:106`）。
- **问题描述**：① 照抄 `.env.example` 的开发者会让 `ai/pg_store.py` 连接不存在的数据库 `matchforge`；连接异常被 `pg_store.py:116-118` 的 `except` 吞掉仅记日志，**会话历史功能静默失效**，界面上表现为"历史会话永远为空"且无任何告警。② 文档宣称的模型与实际调用模型完全不同，任何按文档去开 DashScope 账号/算成本的人都会被误导。
- **可能后果**：隐性功能缺失（会话历史）长期无人发现；对外材料（PRD/架构文档）技术栈失真。
- **推荐解决方案**：以代码现状为真源修订 `环境要求.txt` §六与 `.env.example` 注释；`.env.example:59` 改为 `matchforge_memory`；将 `DASHSCOPE_API_KEY` 别名 `LLM_API_KEY` 提升为正名（代码中已存在别名，`ai/config.py:21`），文档统一写 `LLM_API_KEY`。
- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：不影响进程启动，但影响功能完整性与文档可信度
- **是否需要重构**：否
- **验收标准**：照抄 `.env.example` 后 `init_sessions_table()`（`ai/pg_store.py:61`）无异常日志；`环境要求.txt` 与 `.env.example` 的模型名、库名逐项一致。

### 问题 6：docker-compose 不含后端/前端服务，全仓无 Dockerfile——"一键起"只覆盖数据层
- **所属模块**：部署编排
- **严重程度**：严重
- **影响范围**：部署形态、试点交付、环境一致性
- **发现依据**：`docker-compose.yml` 服务清单仅 7 个 infra 服务（`:20-207`）；Glob 全仓 `{Dockerfile,...}` 仅命中 `deploy/docker-compose.yml` 与一个 `.ps1`；开发文档计划"docker-compose 骨架（…+api+web）"（`docs/AI供需对接平台-项目开发文档.md:203`）未兑现；前端有 `npm run build` 与 `web/dist/`（`web/package.json` scripts），但无任何静态托管/反向代理配置
- **问题描述**：当前"部署"= 人工开 3 个终端分别跑 uvicorn / vite dev / docker compose，进程守护、开机自启、日志收集全无。根目录散落的 `backend_serve.log`、`frontend_serve.log` 正是这种手工 `> log` 运行方式的直接证据。
- **可能后果**：试点客户环境无法标准化交付；演示机重启后服务全丢；任何"把环境给我复刻一份"的需求都要重新人肉踩坑（且踩中问题 1/2/3）。
- **推荐解决方案**（MVP 适度方案，不上 K8s）：① 为 api 写一份基于 `python:3.11-slim` 的 Dockerfile（uvicorn 单容器多 worker 可选 `--workers 2`）；② 为 web 写多阶段 Dockerfile（node 构建 + nginx 托管 + `/api` 反代）；③ compose 增加 `api`、`web` 两个服务，`depends_on` 用 `service_healthy` 挂到 mysql/postgres/milvus 上；④ 保留现有 infra-only 模式供本地开发。配套补 `.dockerignore`。
- **修改成本**：中
- **优先级**：P1
- **是否影响当前上线**：影响"可复制交付"的上线形态；本地演示不影响
- **是否需要重构**：否（纯增量）
- **验收标准**：`docker compose up -d` 一条命令拉起全部 9 个服务，`curl localhost/api/v1/health` 与前端页面均可用；`docker compose restart api` 后服务自愈。

### 问题 7：数据库初始化/迁移四套机制并存，schema 真源不明
- **所属模块**：数据库工程化
- **严重程度**：严重
- **影响范围**：新环境建库正确性、schema 演进可维护性
- **发现依据**：
  - (a) docker 首启自动执行 `deploy/docker/mysql/init/01_matchforge_schema.sql`（含 `DROP TABLE IF EXISTS` 十连，`:14-23`）+ `02_pc_industry_schema.sql`；
  - (b) `api/db_init.py`（310 行）用 SQLAlchemy 另建 `material_dictionary`/`suppliers`（`:43-79`）并导种子；
  - (c) `data/init_all.py` 调宿主机 mysql CLI 执行 `data/mysql_schema.sql`（`:54-65`，该文件与 deploy 01 同源副本，头部注释一致）+ 三个子导入脚本；
  - (d) `database/migrations/02-07` 手工迁移，编号缺 01，`07_user_name_company.sql:11` 自注"可重复执行: 否"；无 alembic、无迁移版本记录表；此外 `api/main.py:52-54` 启动时还会 `kb.db.init_db()`（`kb/db.py:63-67`，`Base.metadata.create_all` 幂等建 kb_* 表）——第五套隐式建表路径。
- **问题描述**：同一个 `suppliers` 表在 01 SQL 与 `db_init.py` 中各有一份 DDL，已开始各自演进；`users` 表的 `name/company` 列在 01 中不存在、靠 07 补、而 07 不可重复执行且无应用记录——"哪个库打过哪些补丁"全靠人脑。`环境要求.txt:115-117` 指定的初始化命令是 `data/init_all.py`，`api/db_init.py:3` 又自称"一键初始化"，入口互相打架。
- **可能后果**：新环境按不同路径初始化得到不同 schema（典型：`users` 缺 `name/company` → auth 路由 AttributeError，07 注释已记录该事故）；试点环境 schema 与开发环境漂移，排障困难。

### 附：当前架构可支撑量级与规模化障碍

**可支撑（原型→小规模试点）【合理推断】**：单 uvicorn + 单套数据容器，支撑内部演示与个位数试点客户、数十并发 SSE 寻源、万级公司知识库（Milvus standalone 百万级向量内无压力）、分钟级 LLM 批量生成（受 `KB_LLM_CONCURRENCY=2` 人为限流保护）没有问题。真正的瓶颈会先出现在 LLM 供应商速率限制，而不是本地架构。

**规模化障碍（按出现顺序）【合理推断】**：① 无容器化应用与进程守护（问题 6/15）→ 试点交付与可用性；② SSE 长连接 + 进程内任务队列绑定单进程 → 多实例扩容前需把 KB 任务队列外移（如 Redis 队列——届时 Redis 才真正有必要，见问题 13）；③ 单 Milvus standalone 与单 Neo4j 社区版无 HA；④ 无 metrics/告警，无法量化容量拐点；⑤ 会话 token 存 MySQL 是好事，多实例 API 本身无需改造会话亲和性（正面，`kb/auth.py:218-226`）。
