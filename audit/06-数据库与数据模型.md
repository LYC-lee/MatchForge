# 数据库与数据模型审计报告

> 审计角色：数据库架构师（只读审计，未修改任何项目文件）
> 审计范围：`database/` 全部、`data/mysql_schema.sql`、`data/milvus_collections.py`、`data/` 种子数据与导入脚本、`api/models*.py`、`api/db/`、`ai/tools/`（mysql/neo4j/milvus client）、`scripts/seed_*`、以及为确认"实际生效的数据层"而延伸阅读的 `kb/`、`api/routers/`、`api/main.py`、`deploy/docker-compose.yml`。
> 标注约定：【已确认事实】= 有直接代码/文件证据；【合理推断】= 由证据链推出但存在反例可能；【尚未验证】= 需要运行时环境确认；【缺少材料】= 仓库中找不到支撑材料。

## 1. 领域概述

### 1.1 仓库中存在三套互相独立、结构互不相同的数据模型

这是本次审计最核心的发现。MatchForge 的"数据库"不是一个 schema，而是至少三套并存：

| 体系 | 定义位置 | 库名 | 规模 | 状态 |
|---|---|---|---|---|
| ① pc_industry 事实库 | `database/01_schema/01_core_tables_ddl.sql`（13 表）+ `database/02_field_dictionary/` + `database/04_seed_data/*.csv`（13 个 CSV） | `pc_industry` | 13 张表，含外键/枚举/审计字段，文档质量最高 | 【已确认事实】被 `deploy/docker/mysql/init/02_pc_industry_schema.sql` 装入 Docker；被 `scripts/import_pc_industry_seed.py` 灌 CSV；【尚未验证】运行时代码是否真正查询它（`kb/config.py:57-61` 的 `COMPANY_MYSQL_URL` 指向它，用于公司库只读快照） |
| ② matchforge 运营库（P4 数据层版） | `data/mysql_schema.sql`（9 表：enterprises/users/buyers/suppliers/qualifications/categories/products/material_dictionary/rfqs/leads） | `matchforge` | 9 张表，无外键外的唯一约束，枚举全用 VARCHAR | 【已确认事实】与 `deploy/docker/mysql/init/01_matchforge_schema.sql` 逐字相同；`ai/config.py:54-61` 的 `MYSQL_URL` 指向该库；`data/init_all.py` + `data/suppliers/import_to_mysql.py`（35 家供应商 JSON）灌数据 |
| ③ kb_/demo_ 表族（实际运行主力） | `kb/models.py`（31 个 ORM 类，`kb_manuals`/`kb_chunks`/`kb_companies`/`kb_rfqs`/`kb_quotations`/`demo_rfqs` 等）+ `database/migrations/02~05` | `KB_DATABASE_URL` 所指库（默认 `mysql+pymysql://…/matchforge`，`kb/config.py:51-54`） | kb_* 约 23 张 + demo_* 8 张 | 【已确认事实】`api/main.py:52-54` 启动时只调用 `kb.db.init_db()`；所有 `api/routers/*` 均通过 `kb.db.session_scope` 读写；`scripts/seed_*.py` 6 个种子脚本全部 `from kb.db import session_scope` |

三套体系中有三张**同名不同构**的核心表：`suppliers`（①有 `company_id` FK + ENUM 状态；②有 `main_category` VARCHAR + `enterprise_id`；③无独立 suppliers 表，供应商以 `kb_companies` 快照 + `kb_company_relationships` 表达）、`rfqs`（①有 `rfq_number UNIQUE` + `part_id` FK；②有 `thread_id`/`parsed_spec`/`normalized_spec` JSON 列；③ `kb_rfqs` 有 `buyer_company_id` + `context_json`）、`categories`（①③无关，①②字段不同）。

### 1.2 ORM 层同样存在三套且其中一套是死代码

- `api/models.py`（SQLite 风格，`String(12)` UUID 主键，Supplier 含 `categories`/`brands`/`moq`/`lead_time_weeks`/`data_source` JSON 列）——【已确认事实】被同名包 `api/models/__init__.py` 遮蔽（Python 包优先于同名模块；实测 `import api.models` 解析到 `api/models/__init__.py`），整文件死代码；引用它的 `api/routes/`（8 个文件）未被 `api/main.py` 注册，整目录死代码。
- `api/models/__init__.py`（双 Base：`MatchforgeBase` + `PcIndustryBase`，`api/models/__init__.py:22-23`）与 `api/db/session.py`（双库 Session 工厂）——【已确认事实】全仓库 grep 不到任何 router/模块引用 `get_matchforge_session`/`get_pc_industry_session`/`MatchforgeBase`（除其自身），是第二套死 ORM。
- `kb/models.py` + `kb/db.py` —— 唯一被 `api/main.py` 激活的 ORM。

### 1.3 四库（MySQL/Milvus/Neo4j/Redis）实际承载

- **MySQL**：两套 schema 同时由 docker-entrypoint-initdb.d 建出（`deploy/docker-compose.yml:39` 挂载 `./docker/mysql/init`）；运行时主要读写 kb_/demo_ 表。
- **Milvus**：两个集合 `product_embeddings`（HNSW/COSINE，`data/milvus_collections.py:117-209`，主键 `product_id` 注释声明"对应 MySQL products.id"——指②号 matchforge.products）与 `knowledge_chunks`（IVF_FLAT）。另在 `kb/vectorstore.py:193+` 有第三个集合 `company_knowledge_chunks`（MilvusVectorStore），KB_VECTOR_STORE 默认 `milvus` 且不可达时降级本地 numpy（`kb/vectorstore.py:333-346`）。
- **Neo4j**：替代料图，`(:Part)-[:EQUIVALENT_TO|CROSS_REF]->(:Part)`（`data/alternatives/import_to_neo4j.py:7-11`），被 `ai/agents/alternatives.py:34-35` 调用；但种子 `data/alternatives/alternatives.json` 仅 **2 条**关系。
- **Redis**：`deploy/docker-compose.yml:192-194` 部署了 redis:7，`ai/config.py:97-100` 定义了 REDIS_URL，但【已确认事实】全仓库（排除 config 自身与注释）**没有任何 `import redis` 或调用方**——纯空跑。
- 另有 **PostgreSQL 16**（`docker-compose.yml:167`）供 `ai/pg_store.py`（AgentMemory），属第五库。

### 1.4 跨库关联与一致性机制

- Milvus `product_embeddings.product_id` ↔ matchforge `products.id`：仅靠离线脚本 `data/milvus_seed_data.py:12`（MySQL→Embedding API→Milvus）一次性同步；`data/suppliers/import_to_mysql.py:103-108` 每次导入前 `TRUNCATE products/suppliers`，【已确认事实】导入脚本不清理 Milvus 对应向量，也不存在任何运行时代码在供应商/产品变更时增删 Milvus 向量。
- kb_companies 与 pc_industry.companies：靠"快照时 `id = 源 company_id`"约定（`database/migrations/02_kb_schema.sql:14-15` 注释），无 FK、无对账任务。
- 替代关系双写：MySQL ①有 `part_alternatives` 表（L1-L5 级），Neo4j 有 EQUIVALENT_TO/CROSS_REF 边，两者无 ID 映射、无同步代码。
- `matchforge.leads.rfq_id` 在 ORM 注释中自述"跨库关联 pc_industry.rfqs.id"（`api/models/__init__.py:70`）——跨库无外键，仅靠注释约束（且该 ORM 本身未被使用）。

### 1.5 逐表审查摘要（①pc_industry，文档质量最高的一套）

- 主键：全部 `BIGINT AUTO_INCREMENT`，合格。
- 外键：齐全且 ON DELETE 策略明确（如 `fk_cs_company … ON DELETE CASCADE`，`01_core_tables_ddl.sql:94`）。
- 唯一约束缺失：`parts.part_number` 仅普通索引（`:128`），同品牌同料号可重复插入；`part_alternatives` 无 `(original_part_id, alternative_part_id)` 唯一约束（`:218-222`），可重复录入同一替代对；`suppliers.name` 无唯一约束。
- 枚举：关键字段用了 ENUM（`lifecycle_status`/`level`/`status`），`confidence_level` 用 VARCHAR(30) 留有扩展，处理得当。
- 时间/审计字段：多数表有 created_at/updated_at；`spec_definitions`/`rfq_suppliers`/`quotations`/`data_sources` 无 updated_at；全库无 created_by/updated_by（rfqs.created_by 是 VARCHAR(50) 孤字段，无 FK）。
- 软删除：无。`02_indexes.sql:29` 注释自述"软删除字段 deleted_at + 索引（第一版未引入）"。
- 反范式冗余：`parts.category_name`、`supplier_capabilities.category_name`、`part_alternatives` 双 part_number 冗余——有注释说明用途，可接受，但无保证一致性的机制。
- 反范式字段：`supplier_capabilities.brand_names VARCHAR(500)` 逗号分隔（`:182`），无法索引、无法 FK。
- 索引：`02_indexes.sql` 补了 4 个复合索引，方向正确；`parts.specs` JSON 检索无函数索引（注释中自承认留作长期扩展）。

## 2. 问题清单

### 问题 1：AI 供应商匹配工具查询的列在真实库中不存在（核心闭环断点）

- **所属模块**：AI 智能体 → MySQL 数据层（②号 matchforge 库）
- **严重程度**：致命
- **影响范围**：README 宣称核心闭环中的"供应商匹配"环节；`ai/agents/match.py:79` → `filter_suppliers_raw`
- **发现依据**：`ai/tools/mysql_client.py:123-131` 查询 `SELECT s.id, s.name, s.category, s.brand_coverage AS brands, s.location, s.moq, s.lead_time_weeks, s.data_source … FROM suppliers s WHERE s.category = :category AND s.status='approved'`；而 `data/mysql_schema.sql:58-74` 的 `suppliers` 表**没有** `category`（只有 `main_category`）、**没有** `brand_coverage`、`moq`、`lead_time_weeks`、`data_source` 任何一列；`database/01_schema/01_core_tables_ddl.sql:156-172` 的 pc_industry.suppliers 同样没有。该 SQL 对任何一套真实 schema 执行都会报 `Unknown column 's.category'`。
- **问题描述**：mysql_client 的字段清单恰好与死代码 `api/models.py` 中的 Supplier（含 `moq`/`lead_time_weeks`/`data_source`/`brands`）一致——开发者对照着一个已被包遮蔽、从未生效的模型写了生产 SQL。同时 `ai/config.py:54-61` 的 `MYSQL_URL` 只连 `matchforge` 库，而物料/供应商事实数据在 `pc_industry` 库，即使列名修正也查错库。
- **可能后果**：寻源 Agent 执行到供应商匹配节点即抛 SQLAlchemy OperationalError，SSE 流中断或返回空结果；演示环境中该链路必然失败或依赖未验证的兜底。
- **推荐解决方案**：先决策唯一事实源（见问题 2），然后按真实 schema 重写 `filter_suppliers`/`filter_suppliers_raw`：若走 pc_industry，应 JOIN `supplier_capabilities`（按 `category_id` + `audit_status='approved'` + `brand_names LIKE`）连 `suppliers`；若走 matchforge，应改列名为 `main_category` 并把 MOQ/交期改查 `products` 表。加一条针对该工具的集成测试（真库或 sqlite-memory 不行，需 MySQL）。
- **修改成本**：低（单文件 SQL 重写）～中（若涉及换库）
- **优先级**：P0
- **是否影响当前上线**：是
- **是否需要重构**：否（但依赖问题 2 的决策）
- **验收标准**：在装有真实 schema 的 MySQL 上直接执行 `filter_suppliers_raw(category='MLCC')` 返回非错误结果；`ai/agents/match.py` 端到端跑通一条 MLCC 寻源请求并返回供应商列表。

### 问题 2：三套同名不同构的供应商/RFQ/品类数据模型并存，事实源不唯一

- **所属模块**：全局数据架构
- **严重程度**：致命
- **影响范围**：所有读写 suppliers/rfqs/categories 的链路（AI 工具、API 路由、种子脚本、Docker 初始化、前端展示）
- **发现依据**：`database/01_schema/01_core_tables_ddl.sql`（13 表，pc_industry）vs `data/mysql_schema.sql`（9 表，matchforge）vs `kb/models.py:500-615`（kb_rfqs/kb_rfq_suppliers/kb_quotations）；三张 `rfqs` 表字段两两不同（`database/01_schema/01_core_tables_ddl.sql:228-249` / `data/mysql_schema.sql:131-145` / `database/migrations/04_rfq_supplier_loop.sql:14-35`）；Docker 启动会同时建出前两套（`deploy/docker/mysql/init/01_matchforge_schema.sql` 与 `02_pc_industry_schema.sql` 分别是两份 DDL 的复制品）。
- **问题描述**：同一业务概念有三份定义：供应商在①是 `suppliers`+`supplier_capabilities`，在②是 `suppliers`+`products`+`qualifications`，在③是 `kb_companies` 快照 + `kb_company_relationships`。RFQ 在①②③各有一张表，状态机枚举还互不相同（②是 draft/sent/quoted/closed；③ kb_rfqs 是 draft/sent/quoted/closed/cancelled）。种子数据也分裂：`database/04_seed_data/05_suppliers_seed.csv`（①结构，立创/云汉等）与 `data/suppliers/suppliers.json`（②结构，35 家）是两套互不相干的供应商事实。
- **可能后果**：新成员（或 AI 编码助手）按任意一套写代码都"看起来对"；数据写入入口不同导致同一实体在不同库中逐渐漂移；问题 1 正是这种分裂的直接产物。继续下去，任何跨表统计、审计、对账都不可信。
- **推荐解决方案**：MVP 阶段收敛为"一套半"：明确 **kb_/demo_ 表族为唯一运行时 OLTP schema**（因为这是 `api/main.py` 实际激活的），pc_industry 13 表降级为只读参考数据集市（改名前缀或独立库保留，仅供 `COMPANY_MYSQL_URL` 快照），`data/mysql_schema.sql` 的 9 表整体废弃（其 suppliers/products 职责已由 kb_* 与 Milvus 分别承担，material_dictionary 若保留需并入 kb schema）。在 `database/README.md` 写明唯一事实源矩阵：每个业务概念 → 唯一表 → 唯一写入入口。
- **修改成本**：中（DDL 废弃 + 文档 + 种子归并；不动运行时代码主路径）
- **优先级**：P0
- **是否影响当前上线**：是（不收敛则问题 1 类错误会持续再生）
- **是否需要重构**：是（数据层归并，非代码重构）
- **验收标准**：仓库全文搜索 `CREATE TABLE.*suppliers`/`CREATE TABLE.*rfqs` 每概念仅剩一处有效定义；docker 初始化只建一套业务表；README/database/README 给出事实源矩阵并被引用。

### 问题 3：两套死 ORM + 死路由目录，且死模型字段"污染"了活代码

- **所属模块**：`api/models.py`、`api/models/__init__.py`、`api/db/session.py`、`api/routes/`
- **严重程度**：严重
- **影响范围**：代码可维护性、新人/AI 助手误导、迁移 06/07 的目标表错位
- **发现依据**：`api/main.py:56-93` 只 `from api.routers import …`，未注册 `api/routes/`；实测 `import api.models` 解析到包 `api/models/__init__.py`（包遮蔽同名模块），故 `api/models.py` 全文死代码；`api/database.py:30` `from api.models import User, Supplier, RFQ, Lead, AuditRecord` 中 `AuditRecord` 在包内不存在，若该函数被调用必 ImportError；`api/db/session.py` 双库工厂在全仓库无调用方（grep 0 命中，除自身）；`api/routers/auth.py:8-10` 实际使用 `kb.auth`（`kb_users`/`kb_sessions` 表），而 `database/migrations/06_enterprise_type.sql:16` 与 `07_user_name_company.sql:16-20` ALTER 的却是 `users` 表——迁移修补的是一个运行时不用的表。
- **问题描述**：死代码不是无害的：`ai/tools/mysql_client.py` 正是照死模型 `api/models.py` 的 Supplier 字段写的 SQL（问题 1 的成因）；迁移 06/07 的注释（"login/refresh/me 路由响应引用 user.name/user.company"）描述的是死路由 `api/routes/auth.py` 的行为。
- **可能后果**：继续诱导后续开发在错误的表上写迁移、在错误的模型上写查询；`users` 表与 `kb_users` 表双账号体系并存，数据分裂。
- **推荐解决方案**：删除（或移入 `archive/` 目录并在 README 标注废弃）`api/models.py`、`api/models/__init__.py`、`api/db/session.py`、`api/routes/`、`api/database.py`；在 `database/migrations/README` 中声明 06/07 仅适用于已废弃的 users 表、新库无需执行；账号体系统一到 `kb_users`。
- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：否（运行时不引用），但直接诱发 P0 级错误
- **是否需要重构**：否（删除即可）
- **验收标准**：删除后 `pytest` 全绿；`grep -rn "api.routes\|api.models import\|api.db.session"` 无命中；迁移 README 有明确说明。

### 问题 4：四库写入无任何一致性保障，Milvus/Neo4j 与 MySQL 必然漂移

- **所属模块**：跨库数据同步（MySQL ↔ Milvus ↔ Neo4j）
- **严重程度**：严重
- **影响范围**：语义搜索召回正确性、替代料推荐正确性
- **发现依据**：`data/suppliers/import_to_mysql.py:103-108` 每次导入先 `TRUNCATE products/qualifications/suppliers/enterprises` 再按 JSON 指定 id 重插；`data/milvus_seed_data.py:12-14` 只在脚本执行时做一次 MySQL→Milvus 全量同步；`kb/vectorstore.py:43` 虽有 `delete_by_company` 接口但【已确认事实】无任何导入/路由代码在产品变更时调用 Milvus upsert/delete（仅 kb pipeline 的 chunk 向量化在用）；Neo4j 与 `part_alternatives` 表之间无任何同步代码（`data/alternatives/import_to_neo4j.py` 只读 alternatives.json）。
- **问题描述**：①MySQL products 每次 TRUNCATE 重灌，Milvus 中的旧 product_id 向量成为孤儿（id 复用后甚至指向错误产品）；②运行时没有"供应商上架产品 → 写 MySQL → 写 Milvus"的任何路径（api/routers 中无产品写入端点）；③替代关系在 MySQL part_alternatives 与 Neo4j 双写，无双向映射。
- **可能后果**：语义搜索召回到已删除/已换主的 product_id；演示中途重灌数据后向量库返回错位结果；替代料答案在图库与关系库中不一致。
- **推荐解决方案**：MVP 不引入消息队列/CDC。落地方案：(a) 导入脚本改为"先删 Milvus 对应 id 段再重灌"，或在 `init_all.py` 中固定执行顺序 `mysql → milvus_collections --drop → milvus_seed_data`（已有顺序，但缺 Milvus 清空步骤的强制化）；(b) 在 kb pipeline 之外补一个 `sync_product_vectors()` 管理命令，供应商产品变更后手动/定时全量重建（MVP 数据量 35 家×产品，全量重建成本秒级）；(c) 替代关系单一事实源二选一：MVP 建议保留 MySQL `part_alternatives`，Neo4j 降级为可选增强（见问题 11）。
- **修改成本**：低～中
- **优先级**：P1
- **是否影响当前上线**：部分（每次重灌种子后即产生脏向量）
- **是否需要重构**：否
- **验收标准**：连续执行两次 `init_all.py` 后，`product_embeddings` 中不存在 MySQL `products.id` 之外的向量（对账 SQL/脚本输出为 0 差异）。

### 问题 5：Redis（及 PostgreSQL）部署但几乎无消费方，MVP 运维面过大

- **所属模块**：基础设施 / `deploy/docker-compose.yml`
- **严重程度**：严重（对 MVP 阶段而言）
- **影响范围**：部署复杂度、资源占用、新人上手成本
- **发现依据**：`deploy/docker-compose.yml:192-194` 定义 redis:7 容器并配置密码；`ai/config.py:97-100` 定义 REDIS_URL；【已确认事实】全仓库无 `import redis`/`from redis` 及任何 Redis 读写调用。PostgreSQL（`docker-compose.yml:167`）仅 `ai/pg_store.py` 使用。 compose 共起 6 个有状态服务（mysql/etcd/minio/milvus/neo4j/postgres/redis）。
- **问题描述**：Redis 是纯死资产；Neo4j 全库仅 2 条替代关系（`alternatives.json`）；Milvus 的 `knowledge_chunks` 集合被 `kb/vectorstore.py:230` 注释自述"缺少 company_id/language 等过滤字段，无法满足公司级 RAG"而弃用另建 `company_knowledge_chunks`——旧集合成为死集合。

- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：否，但显著降低演示环境可靠性
- **是否需要重构**：否
- **验收标准**：compose 服务数 ≤4；`docker compose up -d` 后无"起了但没人连"的容器（以 `ai/config.py` 中无对应未用配置为准）。

### 问题 7：kb_/demo_ 运行时表族零外键、弱约束，脏数据无防线

- **所属模块**：`database/migrations/02_kb_schema.sql`、`03_enterprise_phase2.sql`、`04_rfq_supplier_loop.sql`、`05_demo_scenario.sql`
- **严重程度**：严重
- **影响范围**：报价/线索/库存/BOM 全链路数据质量
- **发现依据**：`kb_rfqs`（`04_rfq_supplier_loop.sql:14-35`）的 `buyer_company_id` 无 FK；`kb_rfq_suppliers.supplier_company_id` 无 FK（仅有 `uq_rfq_supplier` 唯一键，`:47`——这是全 kb 族唯一约束的少数亮点）；`kb_quotations` 无 FK；`03_enterprise_phase2.sql` 的 `kb_product_bom_items.product_id`、`preferred_supplier_company_id`、`kb_production_orders.product_id/customer_company_id`、`kb_shortages.preferred_supplier_company_id` 全部无 FK；状态字段全为 `VARCHAR(20)` + 注释约定（如 `status VARCHAR(20) DEFAULT 'open' COMMENT 'open|confirmed|…'`，`03:57`），数据库层不校验。
- **问题描述**：该族表是实际运行主存储，却完全靠应用层保证引用完整性与枚举合法性。对照组①号 pc_industry 有完整 FK/ENUM，说明团队具备该能力，kb 族是有意（SQLite 兼容）或赶工放弃。

- **推荐解决方案**：保持 SQLite 兼容的前提下最低成本加固：(a) 关键关联（kb_rfqs.buyer_company_id、kb_rfq_suppliers.rfq_id、kb_quotations.rfq_id、kb_product_bom_items.product_id）补 FK（MySQL 迁移文件内追加 ALTER，SQLite 侧由 SQLAlchemy 层 `ForeignKey` 表达即可）；(b) 状态字段在 ORM 层加 `CheckConstraint` 或用 SQLAlchemy `Enum`（`kb/models.py` 内改，不依赖数据库 ENUM）；(c) 对 `kb_shortages` 这类物化表补一条"重建脚本"作为对账兜底。
- **修改成本**：中
- **优先级**：P1
- **是否影响当前上线**：否（应用层暂时兜住），但每多写一条脏数据未来清理成本越高
- **是否需要重构**：否
- **验收标准**：尝试插入 `buyer_company_id=99999999` 的 kb_rfqs 被数据库拒绝；非法 status 写入被 ORM 拒绝；有对应单测。

### 问题 8：pc_industry 事实库缺关键唯一约束，可重复插入同料号/同替代对

- **所属模块**：`database/01_schema/01_core_tables_ddl.sql`
- **严重程度**：中等
- **影响范围**：物料主数据、替代料数据质量
- **发现依据**：`parts` 表 `part_number` 仅 `KEY idx_parts_part_number`（`:128`）无 UNIQUE，且 `(part_number, brand)` 组合也无唯一约束；`part_alternatives` 仅普通索引（`:218-220`），`(original_part_id, alternative_part_id)` 可重复；`suppliers.name`、`companies.name` 均无唯一约束；`company_segments` 无 `(company_id, segment_code)` 唯一约束（`:92-93`）。
- **问题描述**：种子靠 CSV 人工维护时重复不易发生，但一旦开放导入（`03_import_templates/` 存在说明有计划），重复行将直接进入检索结果。

- **修改成本**：低
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：重复插入同 (part_number, brand) 被 1062 错误拒绝；现有种子 CSV 导入后三张表 `GROUP BY … HAVING COUNT(*)>1` 为 0。

### 问题 9：无软删除且多处 ON DELETE CASCADE，报价/RFQ 历史可物理消失

- **所属模块**：`database/01_schema/01_core_tables_ddl.sql`
- **严重程度**：中等
- **影响范围**：审计追溯、报价历史、误删恢复
- **发现依据**：`fk_alt_original/fk_alt_alternative … ON DELETE CASCADE`（`:221-222`）、`fk_rs_rfq/fk_rs_supplier … CASCADE`（`:266-267`）、`fk_quot_rfq/fk_quot_supplier … CASCADE`（`:289-290`）；全库无 `deleted_at`（`02_indexes.sql:29` 注释自承认）。
- **问题描述**：删除一个 part 或 supplier，其全部替代关系、RFQ 关联、报价记录物理级联删除，无回收站。B2B 寻源场景报价历史是有业务价值的证据链。
- **可能后果**：运营误删供应商后历史报价不可查；后续想做"供应商履约分析"无数据。
- **推荐解决方案**：MVP 轻量方案——`suppliers`/`parts`/`rfqs`/`quotations` 加 `deleted_at DATETIME NULL` + 查询层统一过滤（SQLAlchemy 可加 `with_loader_criteria` 或在每个查询显式加条件），外键策略改 RESTRICT；CASCADE 仅保留在真正的从属数据（rfq_suppliers）。
- **修改成本**：中
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：软删除供应商后其 quotations 仍可按 rfq_id 查出；带 `deleted_at IS NULL` 的默认查询不再返回该供应商。

### 问题 10：会话表无过期机制，token 永久有效

- **所属模块**：`kb/auth.py` + `database/migrations/02_kb_schema.sql:180-188`（kb_sessions）
- **严重程度**：中等
- **影响范围**：安全（token 泄漏不可自然失效）、表膨胀
- **发现依据**：`kb_sessions` 表结构为 `token PK, user_id, name, role, account, created_at`，无 `expires_at` 字段；`kb/auth.py` 全文（11 个函数）grep 不到 `expires|ttl|过期` 任何关键词。
- **问题描述**：Bearer token 一旦签发永久有效，只能靠删行吊销。
- **可能后果**：演示账号 token 泄漏后长期可用；session 表只增不减。
- **推荐解决方案**：加 `expires_at DATETIME`（如 7 天滑动过期），`resolve_token` 校验时过滤过期行；或 MVP 更简单：定时清理 `created_at < NOW() - INTERVAL 30 DAY` 的行。
- **修改成本**：低
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：过期 token 调 `/api/v1/auth/me` 返回 401；过期行被清理任务删除。

### 问题 11：Neo4j 替代料图对 MVP 是过早设计（数据仅 2 条），且与 MySQL 替代表职责重叠

- **所属模块**：Neo4j 图库 / `data/alternatives/` / `ai/tools/neo4j_client.py`
- **严重程度**：中等（架构决策层面）
- **影响范围**：部署复杂度、替代料功能的数据来源决策
- **发现依据**：`data/alternatives/alternatives.json` 仅 2 条关系；`database/04_seed_data/06_part_alternatives_seed.csv` 在 MySQL 侧另有 L1-L5 级替代关系种子；`ai/tools/neo4j_client.py:53-63` 的 2 跳传递查询置信度硬编码 `*0.9` 衰减；图查询结果的 `specs` 直接存在关系/节点属性里，与 MySQL parts.specs 无关联。
- **问题描述**：2 条边的"图数据库"用 Cypher 能做的事，MySQL 一张自关联表 + 一次 JOIN 完全等价；但项目为此多维护一个有状态服务、一个导入脚本、一套 @tool。替代关系同时存在 MySQL `part_alternatives` 与 Neo4j 两处且无同步（问题 4）。

- **修改成本**：低（关闭路径）；中（若决定彻底下线）
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否（是降级/开关化）
- **验收标准**：`NEO4J_ENABLED=false` 时寻源闭环仍返回 MySQL 来源的替代料；compose 可不启 neo4j 而全链路通过。

### 问题 12：币种、单位、精度、键名在四套表间互相打架

- **所属模块**：字段级数据字典一致性
- **严重程度**：中等
- **影响范围**：报价对比、前端展示、AI 解析对齐
- **发现依据**：单价类型：pc_industry `quotations.unit_price DECIMAL(12,4)`（`01_core_tables_ddl.sql:278`）vs kb 族 `kb_quotations.unit_price FLOAT`（`04_rfq_supplier_loop.sql:57`）；币种：pc_industry 注释写死 USD（`:237`）vs kb_quotations `currency VARCHAR(10) DEFAULT 'CNY'`（`:58`）；交期单位：matchforge.products `lead_time_weeks`（`data/mysql_schema.sql:109`）vs pc_industry.supplier_capabilities `lead_time_days`（`01_core_tables_ddl.sql:184`）vs kb_rfqs `lead_time_days`；specs JSON 键名：matchforge.products 注释要求"中文键名"（`data/mysql_schema.sql:106`），而 pc_industry parts.specs 与 `spec_definitions.field_name`（英文，`:141`）约定英文键。
- **问题描述**：FLOAT 存金额会产生 0.1+0.2≠0.3 类误差；weeks/days 混用使 AI 匹配与展示换算口径不一；specs 中文/英文键混用使 JSON_EXTRACT 检索（`ai/tools/mysql_client.py:45-48` 用的是英文键 `$.package/$.capacitance`）与种子数据键名是否一致成为暗雷。
- **可能后果**：报价对比排序错误；同一参数在不同链路查不到；金额对账差一分钱级别错误。
- **推荐解决方案**：数据字典层（`database/02_field_dictionary/`）新增一页"单位与精度约定"：金额一律 DECIMAL(12,4) + currency 列；交期统一 days（展示层换算周）；specs 键名统一英文（中文 label 走 spec_definitions.field_label）；kb 族迁移文件追加 ALTER 修正 FLOAT→DECIMAL（MVP 数据量小，成本可接受）。
- **修改成本**：低～中
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：全库搜索不到 FLOAT 类型的金额列；`filter_suppliers` 类 JSON 查询与种子数据键名抽样比对 100% 命中。

### 问题 13：多租户与权限隔离仅在 kb 访问白名单一处，业务表无租户概念

- **所属模块**：`kb_company_access`（`02_kb_schema.sql:171-178`）、enterprises/users 体系

- **影响范围**：多企业 SaaS 化后的数据隔离
- **发现依据**：`kb_company_access` 提供 user→company 白名单，`api/deps.py:10` 的 `can_access_company` 用于公司级 RAG 校验；但 matchforge 库 `enterprises`/`users`（`data/mysql_schema.sql:24-46`）中 `users.role` 取值在迁移 06 已从 buyer/supplier 改为 member/enterprise_admin/platform_admin，历史数据未迁移（`06_enterprise_type.sql:20-23` 自述"历史数据不自动改写"）；`kb_rfqs.buyer_company_id`、`kb_inventory_items.company_id` 等租户字段无 FK 无复合唯一约束之外的隔离强制。

- **修改成本**：低
- **优先级**：P2
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：用 A 公司 token 请求 B 公司的 dashboard/RFQ 接口返回 403/404；权限判断代码集中在一个模块。

### 问题 14：无备份/归档/数据生命周期策略

- **验收标准**：一条命令产出带时间戳的 kb 族表 SQL dump 文件，并能在干净库上恢复。

### 问题 15：JSON_EXTRACT 全表扫描与 LIMIT 20 的慢查询风险（当前低，需埋点）

- **所属模块**：`ai/tools/mysql_client.py`
- **严重程度**：轻微
- **影响范围**：字典查询、供应商过滤响应时间
- **发现依据**：`ai/tools/mysql_client.py:41-50` 对 `material_dictionary` 做 4 个 `JSON_EXTRACT(params, '$.…')` 等值过滤，无任何可用索引；`filter_suppliers` 用 `JSON_CONTAINS(s.brand_coverage, …)`（`:113`）同样不可索引；`02_indexes.sql:25-29` 注释自承认 specs JSON 函数索引"留作长期扩展"。
- **问题描述**：当前种子数据量（字典 4 条、供应商 35 家）下全表扫描无感；但该查询模式一旦数据量上千即成为固定开销，且位于 Agent 链路关键路径。
- **可能后果**：数据量增长后每次寻源都附带全表扫描；LLM 等待工具返回超时。
- **推荐解决方案**：不修结构，先做两件事：(a) 高频过滤字段（package/capacitance/temp_coeff/rated_voltage）在 `material_dictionary` 上生成为列 + 普通索引（MySQL 8 生成列成本极低）；(b) 给两个工具函数加执行耗时日志，设定 >200ms 告警线。
- **修改成本**：低
- **优先级**：P3
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：`EXPLAIN` 显示生成列索引被命中；工具日志包含耗时字段。

### 问题 16：辅助性不一致（编号断档、双 init 脚本复制品、users 双轨）

- **所属模块**：`database/migrations/`、`deploy/docker/mysql/init/`、`data/mysql_schema.sql`
- **严重程度**：轻微
- **影响范围**：可维护性
- **发现依据**：migrations 从 02 开始编号（01 实际在 `01_schema/01_core_tables_ddl.sql`，跨目录编号易误解）；`deploy/docker/mysql/init/01_matchforge_schema.sql` 与 `data/mysql_schema.sql` 是逐字复制品（含 `DROP TABLE IF EXISTS` 段，`data/mysql_schema.sql:13-22`——docker-entrypoint-initdb.d 只在空库执行一次，DROP 段无害，但手工重跑会毁数据）；`kb_inventory_items` 有 updated_at 无 created_at（`03_enterprise_phase2.sql:82-95`）；`02_kb_schema.sql:10` 与 `05_demo_scenario.sql:13` 的执行示例库名一个写 `pc_industry` 一个写 `matchforge`，迁移落库目标靠 `KB_DATABASE_URL` 隐式决定，注释自相矛盾。
- **问题描述**：单点都小，叠加后"这份 SQL 到底该在哪个库执行"成为新人必踩问题。
- **可能后果**：迁移执行到错误的库；手工重跑 schema 脚本清空业务表。
- **推荐解决方案**：docker init 与 data/ 的复制品改为符号链接或构建时拷贝（单一来源）；每份 SQL 文件头强制写明目标库名与危险性（含 DROP 的标"仅初始化"）；删除 data/mysql_schema.sql 中的 DROP 段或移入独立的 `reset.sql`。
- **修改成本**：低
- **优先级**：P3
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：同内容 SQL 文件全仓库仅存一份；每份文件头有目标库标注。

## 4. 领域评分

### 评分 A：pc_industry 事实库（13 表）单点设计质量 —— **7 / 10**

依据：主键/外键/ON DELETE 策略/ENUM/审计字段/复合索引/字段字典/命名规范/导入模板/ER 图一应俱全（`01_core_tables_ddl.sql`、`02_indexes.sql`、`02_field_dictionary/01_field_dictionary.md`），在 16 小时冲刺约束下是合格甚至偏优的底稿。扣分点：缺关键唯一约束（parts、part_alternatives、company_segments）、无软删除且报价链路全 CASCADE、brand_names 逗号分隔反范式、specs JSON 无可索引路径。

### 评分 B：数据层整体落地一致性与可运维性 —— **3 / 10**

依据：三套同名不同构 schema 并存且事实源从未收敛（问题 2）；AI 关键工具对照死模型写 SQL，核心闭环的"供应商匹配"在真实库上必然报错（问题 1）；两套死 ORM + 死路由目录持续误导开发（问题 3）；Milvus/Neo4j 与 MySQL 之间无任何一致性机制且 TRUNCATE 重灌必然产生孤儿向量（问题 4）；Redis/Postgres/Neo4j 六个有状态服务对当前数据量（35 供应商、2 条替代边）明显过早设计（问题 5、11）；迁移/种子 9+ 脚本三处分散、幂等性不一（问题 6）。运行时实际依赖的 kb_ 族表反而是四份 schema 中约束最弱的一份（零 FK、VARCHAR 枚举、FLOAT 金额）。

**给 MVP 阶段的一句话结论**：不要急着补功能，先做一次"事实源收敛"——确定 kb_/demo_ 为唯一 OLTP schema、pc_industry 为只读参考集市、下线 Redis/Neo4j 为可选组件、删除死 ORM、重写 mysql_client。这五件事均为低～中成本，做完后数据层评分可从 3 提升到 6 以上，且全部不改变现有产品功能。
