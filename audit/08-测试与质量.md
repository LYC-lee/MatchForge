## 2. 问题清单

### 问题 1：全套件运行时 test_kb_rag.py 的数据库隔离失效，会写入真实开发库并调用付费 LLM

- **所属模块**：tests/ 基础设施（conftest + test_kb_rag）
- **严重程度**：致命
- **影响范围**：开发数据库数据安全、API 费用、测试可用性
- **发现依据**：
  - `tests/test_kb_rag.py:29` `os.environ.setdefault("KB_DATABASE_URL", sqlite ...)` 在**模块 import 时**执行；
  - `kb/config.py:51-53` `KB_DATABASE_URL = os.getenv(...)` 为 **import 期常量**，`kb/db.py:13` 冻结引用；
  - pytest 按字母序收集，`tests/test_auth_security.py:48`（a 开头，先于 k 开头）模块级 `from kb.db import session_scope` → kb.config 在 test_kb_rag 的 setdefault 执行**之前**已冻结为 MySQL 默认值；
  - 本机 `.env` 真实生效（`kb.config.llm_available()` 实测为 True），test_kb_rag 无任何强制离线 fixture（对比 test_demo_scenario.py:65-70 有 `_offline_rag`）；
  - 实测：带 key 运行 test_kb_rag 卡死在 `kb_setup` fixture（test_kb_rag.py:48-62）>120s（真实 LLM 逐公司生成）。
- **问题描述**：单独跑 `pytest tests/test_kb_rag.py` 时 sqlite 隔离有效；但**全套件运行**时 setdefault 失效，该文件的 `init_db()`、`collect_companies()`、`generate_for_company(force=True)`（对 company 1/8/13 先删后建手册与 chunk）、`rebuild_vector_index()` 将直接作用于 dev MySQL `matchforge` 库，同时以真实 DashScope Key 逐公司生成 4 份手册——污染/覆盖开发数据并产生 API 费用。文件 docstring（test_kb_rag.py:17-18）宣称"使用独立测试库，不触碰正式数据……无需 Docker/API Key"，在全套件场景下两条均不成立。
- **可能后果**：开发者的知识库数据被测试反复重建（force=True 是删除式重建）；CI/本地一键 `pytest` 变成危险操作；测试运行时间不可控（实测 >120s 无法完成 30 例）。
- **推荐解决方案**：
  1. 在 `tests/conftest.py` 顶部（任何 kb/ai/api import 之前）统一 `os.environ["KB_DATABASE_URL"] = "sqlite:///<临时目录>/kb_test.db"`（注意用 `[]` 赋值而非 setdefault，并在 session fixture 中建临时目录），使全套件共享同一隔离库；
  2. 给 test_kb_rag.py 增加模块级 autouse fixture：`patch("kb.rag.llm_available", return_value=False)` + `patch("kb.config.embedding_available", return_value=False)`（仿 test_demo_scenario.py:65-70 的 `_offline_rag`）；
  3. 若确需"真实生成"冒烟，单独打 `@pytest.mark.live` 标记，默认 `-m "not live"` 跳过。
- **修改成本**：中
- **优先级**：P0
- **是否影响当前上线**：否（但直接威胁开发数据与协作效率，属上线前必须修）
- **是否需要重构**：否（仅测试基建调整）
- **验收标准**：① 一键 `pytest tests/` 全程不连接 3306/19530（可用端口监控或 mock 断言验证）；② 运行前后 dev 库 `kb_manuals`/`kb_chunks` 行数不变；③ 全套件无真实 API Key 时可完整跑完。

### 问题 2：test_kb_rag.py 在无 Key 环境 2 例失败、有 Key 环境实质不可用，30 例长期失管

- **所属模块**：tests/test_kb_rag.py + kb/pipeline + kb/generator
- **严重程度**：致命
- **影响范围**：企业知识库 RAG 的全部回归保障（11 个测试类、30 例）
- **发现依据**：实测清空 `DASHSCOPE_API_KEY/LLM_API_KEY/EMBEDDING_API_KEY` 后 `28 passed, 2 failed in 123.33s`；失败项 `TestLanguageIsolation::test_en_query_recalls_en_first`（`assert 0 >= 3`，英文 chunk 未生成）与 `TestFactualHallucination::test_no_fabrication_for_nonexistent`；失败日志 `kb/pipeline.py:276` → `kb/generator.py:533/542` `RuntimeError: LLM ... generation failed`。`.pytest_cache/v/cache/lastfailed` 记录该文件 4 例长期失败。
- **问题描述**：该文件的 30 个用例**在两种环境下都不能绿**：无 Key 时生成器直接抛错导致下游断言失败；有 Key 时 fixture 真实生成 3 家公司知识，耗时不可接受且消耗 token。即知识库 RAG（公司隔离、防幻觉、幂等、向量重建——其中多条是 P0 级安全特性）**当前没有任何可用的自动化回归**。
- **可能后果**：跨公司数据串读（TestCompanyIsolation）、防幻觉（TestFactualHallucination）等安全红线将来被破坏时无人发现。
- **推荐解决方案**：
  1. 短期：为 kb/generator.py 增加确定性本地降级生成器（基于 `data/` 种子 CSV 模板化生成中英手册），使无 Key 时 30/30 通过；

  3. 修复 `test_en_query_recalls_en_first` 的断言前提（确保 en chunk 存在）或显式 skip 并注明原因。
- **修改成本**：中
- **优先级**：P0
- **是否影响当前上线**：是（知识库是 RAG 匹配与防幻觉红线的载体，其回归全灭）
- **是否需要重构**：部分（generator 需补降级路径）
- **验收标准**：无任何 API Key、无 Docker 环境下 `pytest tests/test_kb_rag.py` 30/30 通过且 <60s；CI 中该文件为必跑门禁。

- **影响范围**：Prompt/模型迭代的回归门禁（#21 宣称的门禁）
- **发现依据**：`scripts/_merge_eval_parts.py` 末段 `for path in ("scripts/eval_current.json", "scripts/eval_baseline.json"): json.dump(out, ...)`——同一份结果同时立为"当前"与"基线"；实测两文件内容完全相同；`eval_agent.py:16-17` 宣称"改 prompt 的 PR 必须附 eval 前后对比"；基线摘要 `accuracy=0.0`、spec_parse 0/8、alt_recommend 0/4、supplier_match 0/5、overall_pass_rate=0.4。
- **问题描述**：① 门禁机制被实现抵消——每次合并分片都覆盖基线，`--compare` 恒无差异；② 现存基线记录的是"解析/替代/匹配三项全挂"的状态，说明评测跑完无人看结果、无阈值拦截；③ chat 类仅 1 条且判据为"回复长度>5"（eval_agent.py:209-229）。
- **可能后果**：prompt 改动导致核心链路退化时对比门禁不会报警；当前 0.0 的 accuracy 意味着"AI 解析规格"这一核心能力在真实评测集上可能已坏（或由评测脚本 `_infer_spec_from_query` 启发式构造输入过糙导致——【尚未验证】根因，需 AI 负责人复核）。
- **推荐解决方案**：① baseline 改为只读归档（git 管理、只允许显式 `--baseline` 更新且需 PR 评审）；② `_merge_eval_parts.py` 只写 current；③ 在 eval_agent.py 增加退出码阈值（如 accuracy < 0.8 或 overall < 0.9 时 exit 1）供 CI 调用；④ 扩充 chat 与多轮场景。
- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：是（宣称的质量门禁实际不存在）
- **是否需要重构**：否
- **验收标准**：人为改坏一个 prompt 后 `eval_agent.py --compare` 能输出非零差异并以非零码退出；baseline 文件 git diff 必须伴随人工说明。

### 问题 6：核心闭环的链路级测试断言过浅——只验事件类型，不验业务结果

- **所属模块**：tests/test_supervisor.py
- **严重程度**：中等
- **影响范围**：parse→normalize→alternatives→match→gen_rfq→grade 全链路回归
- **发现依据**：`test_supervisor.py:74-110` `test_run_procure_stream_spec_phase` / `test_run_procure_stream_match_phase` 仅断言事件序列含 `start`/`result`/`end`，**未解析 result 事件 payload** 校验 parsed_spec 字段、matched_suppliers 非空、rfq_doc 含 "RFQ-ID"、lead_grade 合法。
- **问题描述**：闭环"每个 agent 都返回垃圾但流程走完"也能通过该测试。单元测试各自 mock 了上游输入（如 conftest.py:83-88 直接给 normalized_spec），唯一把 6 个 agent 串起来跑的测试却不验产出。
- **可能后果**：agent 间状态契约（state 字段名、类型）漂移时单测全绿、链路全挂。
- **推荐解决方案**：在现有两个用例上补断言：解析 result payload 的 `parsed_spec.category == "MLCC"`、`matched_suppliers` 非空且含 `match_score`、`rfq_doc` 含 "RFQ-ID"、`lead_grade.grade in {"A","B","C","D"}`。
- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：故意把 gen_rfq_agent 的 rfq_doc 置空时该用例失败。

### 问题 7：全套件运行时长与可用性差（>300s 且卡死），无快慢分层

- **所属模块**：tests/ 全局 + pytest 配置

- **影响范围**：开发者反馈环、CI 可行性

- **修改成本**：低
- **优先级**：P1
- **是否影响当前上线**：否
- **是否需要重构**：否
- **验收标准**：`pytest -m "not slow and not live"` <60s 全绿；全套件（含 slow）<5 分钟。

### 问题 8：弱断言与恒真断言

- spec_parse 0/8 是产品能力问题还是评测脚本 `_infer_spec_from_query` 的构造问题。
- 团队的 dev 流程是否依赖"测试写共享库"这一行为（例如演示数据本就由这些 seed 维护）。

**【缺少材料】**
- 无 CI 历史、无历史覆盖率报告、无 pytest 配置，无法评估通过率的历时趋势。
- 无需求侧对"最低测试范围"的书面约定。
