# 第一部分：项目整体理解

## 1. 项目定位

**宣称（README）**：AI 供需对接平台——采购自然语言描述需求 → AI 解析规格 → 替代料推荐 → 供应商匹配 → 生成询价单 → 分级线索推给上游。

**PRD 自我约束（更可信）**：首期是**单边采购寻源工具**（电子元器件替代料寻源助手），明确不做双边平台、不做交易、不做完整 BOM 优化（`docs/AI供需对接平台-产品需求文档.md:20,57-67`）。

**代码实际形态【事实】**：**三套产品并存**——
1. **AI 寻源对话工具**（与 PRD 对齐）：`/chat` + `POST /procure/stream` + LangGraph 8 节点链（chat→parse→normalize→alternatives→match→rag_enrich→gen_rfq→grade）；
2. **企业经营驾驶舱**（PRD 非目标，继承自旧"电脑元件客服 MVP"）：驾驶舱/BOM/订单/预测/缺件 8 端点 + 3 个前端页，且是**登录后首页**；
3. **企业级 RFQ 双边闭环**（PRD 外产物）：`kb_rfqs/kb_rfq_suppliers/kb_quotations` 真实落库的 RFQ→线索→报价→对比→审核链路 + 供应商工作台 3 页。

另加：演示沙盘（18 个 `/demo/*` 端点、8 张 `demo_*` 表）+ 企业知识库 RAG（双语生成、公司级隔离检索）。

**定位判断**：PRD 本身清晰克制，但**执行层定位漂移**——代码体量最大的部分是 PRD 明确不做的驾驶舱与 RAG 问答，登录首页是驾驶舱而非寻源。当前产品事实上是"带 AI 寻源功能的企业驾驶舱"，楔子（替代料寻源）被稀释。【推断，证据见 01 报告问题 7】

## 2. 用户角色与核心业务流程

**角色**：采购方（buyer/member）、供应商（supplier）、平台管理员（admin）、演示账号（demo）。角色体系已定义但**前端无角色分流、后端注册可自选 admin**（见缺陷 B1）。

**主流程（宣称六环）逐环验证**：

| 环节 | 状态 | 关键证据 |
|---|---|---|
| ① 需求输入 | ✅ 真实 | ChatView + `/procure/stream` |
| ② AI 解析规格 | ✅ 真 LLM | `ai/agents/parse.py`（重/轻模型两级降级+正则前置+白名单校验） |
| ③ 替代料推荐 | ✅ 真 LLM+代码校验层，但数据仅 36 组 | `alternatives.py`（Neo4j+RAG 工具+幻觉校验层+4 红线） |
| ④ 供应商匹配 | ⚠️ 真实但**SQL 查错列/错库** | `match.py:79`→`mysql_client.py:123` 查 `s.category` 等不存在列 |
| ⑤ 询价单生成 | ⚠️ 半实现：**内存模板，不落库** | `gen_rfq.py:80` `rfq_id=MF-{date}-{uuid}` |
| ⑥ 线索分级推上游 | ❌ **断裂**：仅 SSE 返回，无持久化无推送 | `grade.py:50`，全仓 grep 无 DB 写入点 |

**真正可用的闭环在另一条路**（`rfqs.py`+`supplier_leads.py`，缺件页手工 RFQ→发送→供应商报价→比价→审核），但**与 AI 寻源链完全断开**——这是全项目最重要的结构性发现：两条 RFQ 体系字段、ID、入口互不相通。

**未闭环环节**：AI 询价→真实发送（断）、报价回收进 AI 链（断）、用户反馈（无）、供应商入驻（无）、低置信替代人工审核（无队列）。

## 3. 系统架构（文字版）

```
[Vue3+TS+Pinia SPA] 28 路由 / 懒加载 / 自研 SSE 解析 / DOMPurify
   │  axios 统一实例（Bearer 注入、401 队列）＋ 裸 fetch SSE（无 token）
   ▼
[FastAPI 单体 api/main.py] 12 活路由（routers/）＋ 8 死路由（routes/，未挂载）
   │  鉴权：kb/auth.py 会话 token（bcrypt，无过期）＋ 死代码 JWT（硬编码默认密钥）
   ├──► [LangGraph ai/] Supervisor(LLM 路由) + 8 agent
   │      ├── MySQL 工具（供应商/字典，SQL 列名与真实 schema 不符）
   │      ├── Neo4j 工具（替代图，仅 2 条边）
   │      ├── kb RAG 工具（无租户上下文）
   │      └── PG pg_store（会话快照，可选依赖）
   ├──► [kb/] RAG 全链路：种子→LLM 双语生成→语义分块→bge-m3→Milvus/本地向量
   │      ＋ 31 个 ORM 模型（kb_* 23 表 + demo_* 8 表，运行时主存储，零外键）
   └──► [MySQL] 三套 schema 并存：pc_industry(13 表) / matchforge(9 表) / kb_+demo_(31)
[基础设施 compose] MySQL+Milvus(etcd+MinIO)+Neo4j+Postgres+Redis（Redis 零消费方）
[观测] ai/monitor.py jsonl（trace 空转）＋ RagTrace 表；无 metrics/告警/CI/备份
```

## 4. 重点风险区域（审计前预判 → 验证结果）

| 预判风险 | 验证结果 |
|---|---|
| 双路由并存 | ✅ 证实且更糟：死模型字段污染了活代码（mysql_client 照死模型写 SQL） |
| 四库过重 | ✅ 证实：Redis 零调用方、Neo4j 仅 2 条边、PG 为可选依赖 |
| AI 闭环真实性 | 部分推翻：5 个 agent 真调 LLM 且有严肃幻觉校验层（好于预期）；但 match/gen_rfq/grade/rag_enrich 无 LLM，且闭环后两环断裂 |
| 页面-后端一致性 | ✅ 证实多处断裂（发送仅前端 flag、SupplierProducts 纯假数据） |
| 测试有效性 | 部分推翻：单测质量高于预期（804 断言、元测试）；但体系失效（无 CI、kb_rag 两环境不绿、eval 门禁被自身抵消） |
| 商业化路径 | ✅ 证实为最大风险：唯一变现假设未验证、数据差 4-5 个数量级、闭环断在 RFQ |

## 5. 缺少的关键材料

- 真实用户/试点客户使用数据与访谈记录（PRD 列了访谈问题，无执行证据）
- 生产/演示环境部署拓扑（TLS、反代、防火墙）与 `.env` 实际值（敏感文件未读取，合规）
- LLM 配额与成本数据（仅有 429 耗尽日志佐证无成本观测）
- 竞品替代推荐准确率的第三方测评（各家均无可信数据）
- 团队对 Redis/MinIO/Neo4j 的真实排期（决定僵尸服务处置方向）

为中小硬件制造商/EMS 采购解决"缺货找替代料+找供应商"的 10 分钟决策问题。代码实际还承载了企业经营驾驶舱与演示沙盘两个附加命题（定位漂移）。

**2. 当前项目最大的三个优点是什么？**
① AI 寻源链真实且严肃：5 个 agent 真调 LLM，alternatives 有代码级幻觉校验层+4 条红线+置信度上限，是同类 MVP 中少见的成熟设计；② 企业级 RFQ→报价→审核闭环真实落库可用（rfqs.py 体系），不是页面摆设；③ 测试资产底子好：291 用例 804 断言无假测试，含防幻觉元测试。

**3. 当前项目最严重的十个问题是什么？**
① 注册可自选 admin（B1）；② /procure/* 无鉴权（B2）；③ 企业数据默认全通（B4）；④ AI 询价/线索不落库、两套 RFQ 断开（C1/D1）；⑤ 供应商匹配 SQL 查错列错库（A4）；⑥ 三套 schema 事实源不唯一（C2）；⑦ 数据规模差竞品 4-5 个数量级且补数路径有合规风险（I1）；⑧ 唯一变现假设未验证（I2）；⑨ 无 CI 且知识库测试两环境不绿（G2/A6）；⑩ 按文档无法启动（A1/A2/A3）。

**4. 哪些问题会导致项目无法上线？**
A1/A2/A3（起不来）、B1/B2/B3/B4（公网即事故）、E2（演示路径空白）。

**5. 哪些问题会导致上线后出现严重事故？**
B5（弱口令拖库）、B7（LLM 刷量+爆破）、C6/C7（脏数据/500）、E7（用户拿 mock 假数据做采购决策）、F1+F2+G17（LLM 成本失控且无告警，已有 429 实证）、A5（知识库静默为空）。

**6. 哪些功能只是表面完成，实际上没有形成业务能力？**
AI 询价单"发送"（前端 flag）；线索分级"推上游"（无推送）；供应商产品管理（纯本地假数据）；长期记忆（重启即丢）；Redis 限流/缓存（零调用方）；MinIO 对象存储（零代码）；/admin/metrics（不存在）；eval 质量门禁（被自身抵消）；登录响应的 role（硬编码）。

**7. 当前项目最缺的是技术、产品、数据、客户还是商业模式？**
**客户与数据，其次是商业模式验证**。技术原型已超水平；缺的是：真实客户陪跑（0 家）、够用的数据规模（差 4-5 个数量级）、以及"谁付钱"的验证。

**8. 当前项目与头部企业的核心差距是什么？**
数据（SKU/实时价格库存/EOL 情报，差 4-5 个数量级）、交易闭环（竞品推荐挂在可成交库存上）、信任基础设施（质检/担保/审核）、流量入口（EDA/SEO/API 生态）。这四项都不是开发能短期解决的。

**9. 哪些差距可以在三个月内缩小？**
工程差距全部（安全、CI、事实源、容器化）；功能差距大部分（报价回收比价、审核队列、反馈、预警 MVP、入驻审核流）；数据差距可缩小到"两品类够用"（官方 API+人工 curate 5000 条级）。

**10. 哪些差距需要长期积累？**
供应商/原厂关系网络、真实交易数据飞轮、品牌与流量入口、正品信任体系、资金牌照类能力。

**11. 当前是否应该继续增加功能？**
**不应该**。应先修 P0、打通闭环后半程、收敛产品线。唯一例外是报价回收+比价（D5）——它是闭环缺失段而非新功能。

**12. 哪些功能应该删除、合并或推迟？**
删除：api/routes 死代码、views/demos、Redis 服务、死 JWT 体系、GradeCard/QueryInput 死组件。合并：两套 RFQ 体系统一到 RfqRecord；ProcureView 并入 ChatView（中期）；seed_enterprise_* 三脚本合一。推迟：驾驶舱 Phase2 深化、协同/企业问答、Neo4j 扩展、BOM 批量、企业组织审批（到阶段三/四）。

**13. 下一阶段最重要的唯一目标是什么？**
**让 5 家真实采购在打通的闭环上完成"需求→替代→询价→收到真实报价→比价"，并记录每一步转化数据。** 一切工作为此让路。

**14. 当前项目是否值得继续投入？**
**值得，但有条件**：必须在 4-6 周内完成 P0 修复+闭环打通，并在 90 天内拿到"供应商/采购任一方愿意付费"的证据。若 90 天商业验证失败，按 PRD 预案转采购侧 SaaS 订阅再验证一次；再失败则止损。技术资产（AI 校验层、RFQ 闭环、测试套件）在两种转型中都可复用。

**15. 如果只允许投入一个月，最应该完成哪些工作？**
第 1 周：P0 安全+启动+UI 五连修+mysql_client（任务 1-5）；第 2 周：AI 询价落库打通+CI+测试修复；第 3 周：报价回收比价+事实源收敛；第 4 周：产品收敛（首页/Landing）+3 家真实采购陪测并记录转化数据。
