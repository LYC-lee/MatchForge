## 1. 背景

审计确认: AI 寻源链路 (`ai/agents/gen_rfq.py` + `ai/graph.py` SSE) 与真实 RFQ 闭环 (`api/routers/rfqs.py` 落 `kb_rfqs`/`kb_rfq_suppliers`) 是断开的两套系统。

- AI 侧产出纯内存态: `rfq_doc` (文本) / `rfq_id` (临时 `MF-YYYYMMDD-XXXX`) / `lead_grade` / `matched_suppliers[].match_score`, 从不写任何 DB 表。
- 真实闭环侧由 `ShortageProcurementView.vue` 手工拼装 `RfqCreate` 调用, 不消费 AI 产物。
- 前端 `stores/procure.ts:markRfqSent()` 只翻转本地 `rfqSent` flag, 不调任何后端接口。
- `kb_rfq_suppliers.match_score/match_reason` 两列存在但 `create_rfq` 建链时全留 NULL (孤儿列)。
- `RfqCreate.supplier_candidates: list[int]` 只接 company_id, 丢了 score/reason; `lead_grade` 无落点。

## 2. 设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 桥接位置 | 前端显式发送 | 用户可在发送前编辑 RFQ; AI 链路不耦合 DB 写入, 测试隔离简单 |
| demo 边界 | 仅正式模式接通 | `demo_calc.generate_rfq` 入参基于缺件, 与 AI 产物结构差异大且不接受外部候选; 保持 `demo_*`/`kb_*` 表隔离, 满足"边界清晰"验收 |
| 字段归属 | match_score/reason 落 RfqSupplierLink, lead_grade 落 context_json | 复用现有孤儿列, 不改表结构; 语义清晰 (单供应商匹配分 vs 整体商务分级) |
| ID 统一 | 以 RfqRecord.id/rfq_number 为准 | 落库后前端展示 rfq_number (RFQ-YYYY-NNNN) 替代 MF- ID; 满足"DB 出现真实记录非内存 ID" |

## 6. 风险与遗留

- `normalizedSpec` 字段映射缺字段时用默认值 (quantity 默认 1, lead_time 缺则不传), 不阻断发送。
- `selectedSuppliers` 为空时用全部 `matchedSuppliers`; 允许无候选发送 (符合 create_rfq 现有行为)。
- demo 模式 AI 寻源仍不落库 (设计决策); 若后续需要 demo 也接通, 需适配 `demo_calc.generate_rfq` 接受外部候选供应商, 成本较高。
- 浏览器运行时验收 (发送按钮实际点击、错误条展示) 移交 QA。
