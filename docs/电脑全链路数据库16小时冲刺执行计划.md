# 电脑全链路数据库 16 小时冲刺执行计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 16 小时内交付一套可演示、可扩展的电脑全链路数据库最小底座，支撑产业链公司库、物料规格库、供应商能力、替代关系和 RFQ 询价的第一版闭环。

**Architecture:** 16 小时内只做最小事实源和样例数据，不做完整 ERP/MES。MySQL 作为第一版结构化数据主库；Neo4j、Milvus、MinIO 只定义接入边界和同步字段，暂不强制完成全量接入。

**Tech Stack:** MySQL 8.0、CSV/Excel 数据模板、FastAPI/SQLAlchemy 后续接入预留、Neo4j/Milvus 字段映射预留。

---

## 1. 16 小时目标

这次冲刺不是要做完整电脑产业链数据库，而是要在一天内做出一个“能开始录数据、能支撑 Demo、后续能扩展”的最小版本。

最终交付物：

- 数据库模块边界：明确第一版建哪些表，不建哪些表。
- 字段字典：每张核心表的字段、类型、说明、示例值。
- 导入模板：公司、物料、供应商、替代关系、RFQ 的 CSV/Excel 模板。
- 首批样例数据范围：建议 30 家公司、50 条物料、20 家供应商、30 组替代关系、5 个 RFQ 样例。
- 产品闭环验收：能从“物料需求”走到“候选物料、替代料、供应商、询价单”。

## 2. 压缩后的范围

### 必做

- 产业环节库
- 公司库
- 品类库
- 物料库
- 规格字段定义
- 替代关系库
- 供应商能力库
- RFQ 询价库
- 报价记录库
- 数据来源和可信度字段

### 暂不做

- 完整采购订单
- 库存批次
- 生产工单
- 质量检验
- 售后 RMA
- 复杂权限系统
- 复杂审批流
- 全量 Neo4j/Milvus 同步

这些内容只保留后续扩展字段或表名，不进入 16 小时冲刺交付。

## 4. 小时级任务清单

### 0-1h：冻结范围

- [ ] 确认首批只覆盖 `MLCC、SSD、DRAM、连接器、散热` 5 个品类。
- [ ] 确认首批只覆盖 `元器件、模组、分销、ODM/EMS、检测认证` 5 个产业环节。
- [ ] 确认第一版闭环为：`需求 -> 物料 -> 替代料 -> 供应商 -> RFQ`。
- [ ] 明确不做采购、库存、生产、质量、售后流程。

**验收：** 团队接受 16 小时内只做“数据库最小底座”，不追求完整全链路。

### 1-3h：核心表设计

- [ ] 设计 `industry_segments`：产业环节。
- [ ] 设计 `companies`：公司主体。
- [ ] 设计 `company_segments`：公司和产业环节关系。
- [ ] 设计 `categories`：物料品类。
- [ ] 设计 `parts`：物料主数据。
- [ ] 设计 `spec_definitions`：品类规格字段定义。
- [ ] 设计 `suppliers`：供应商主体。
- [ ] 设计 `supplier_capabilities`：供应商能力。
- [ ] 设计 `part_alternatives`：替代料关系。
- [ ] 设计 `rfqs`：询价需求。
- [ ] 设计 `rfq_suppliers`：询价目标供应商。
- [ ] 设计 `quotations`：报价记录。
- [ ] 设计 `data_sources`：数据来源。

**验收：** 能画出第一版 ER 关系：公司属于环节，物料属于品类，供应商有能力，物料有替代关系，RFQ 关联物料和供应商。

### 3-5h：字段字典

- [ ] 为 `companies` 定义字段：名称、别名、国家、地区、官网、简介、可信度、来源、更新时间。
- [ ] 为 `parts` 定义字段：型号、品牌、品类、参数 JSON、生命周期、来源、更新时间。
- [ ] 为 `supplier_capabilities` 定义字段：供应商、品类、品牌覆盖、MOQ、交期、地区、审核状态。
- [ ] 为 `part_alternatives` 定义字段：原型号、替代型号、替代等级、参数差异、风险说明、来源、审核状态。
- [ ] 为 `rfqs` 定义字段：需求描述、目标物料、数量、交期、目标价、状态。
- [ ] 为 `quotations` 定义字段：RFQ、供应商、单价、MOQ、交期、有效期、备注。

**验收：** 每个字段有中文名、英文名、类型、是否必填、示例值。

## 7. 10-12h：MySQL DDL 草案

第一版只需要写核心表 DDL，不追求复杂索引和所有外键。

必须包含：

- [ ] `industry_segments`
- [ ] `companies`
- [ ] `company_segments`
- [ ] `categories`
- [ ] `parts`
- [ ] `spec_definitions`
- [ ] `suppliers`
- [ ] `supplier_capabilities`
- [ ] `part_alternatives`
- [ ] `rfqs`
- [ ] `rfq_suppliers`
- [ ] `quotations`
- [ ] `data_sources`

字段设计原则：

- 所有表都有 `id`、`created_at`、`updated_at`。
- 关键业务表都有 `source_id` 或 `source_name`。
- 物料规格优先用 `specs JSON`，避免一开始为每个品类建大量列。
- 替代关系必须有 `level`、`confidence`、`risk_note`、`review_status`。
- 供应商能力必须有 `category_id`、`brand_names`、`moq`、`lead_time_days`。

**验收：** DDL 能表达第一版业务闭环，后续可以迁移到 SQLAlchemy/Alembic。

## 8. 12-14h：闭环验证

用样例数据手动验证 3 条链路：

### 链路 A：缺货找替代

```text
输入：TMK212BJ105KG-T 缺货
查 parts 找到原型号
查 part_alternatives 找到 2-3 个替代型号
查 supplier_capabilities 找到覆盖品牌/品类的供应商
生成 RFQ
```

### 链路 B：按参数找候选物料

```text
输入：0805 1uF X5R 25V MLCC
查 categories 找到 MLCC
查 parts.specs 匹配规格
返回候选型号
匹配供应商
```

### 链路 C：BOM 风险预演

```text
输入：一份 10 行样例 BOM
逐行匹配 parts
缺失项标记为 unknown
有替代关系的物料返回替代建议
无供应商能力的物料标记供应风险
```

**验收：** 三条链路都能用样例数据解释清楚，不依赖 LLM 编造事实。

## 10. 16 小时后的下一步

16 小时结束后，不要马上扩展到制造和质量，建议按这个顺序继续：

1. 把 DDL 落到 `deploy/docker/mysql/init` 或后端迁移目录。
2. 建立 SQLAlchemy Model。
3. 做 CSV 导入脚本。
4. 做公司、物料、供应商、替代关系的管理 API。
5. 接入现有 AI 寻源流程，让推荐结果只从数据库取事实。
6. 再接 BOM 导入和 BOM 风险分析。

## 11. 成功标准

16 小时冲刺成功，不是看数据多，而是看是否满足以下标准：

- 数据结构能支撑 `需求 -> 物料 -> 替代料 -> 供应商 -> RFQ`。
- 每条关键数据都有来源和可信度。
- 样例数据能演示 3 条业务链路。
- 表结构没有绑定单一品类，后续能扩展到更多电脑零部件。
- 团队知道下一步应该录什么数据、建什么表、接什么 API。
